## Owner decisions

- Boxed CLI UI is a must.
- Shell, one language. Must run on macOS bash 3.2 on the laptop; the server side may use bash 5.
- Admin-only: the tool uses the admin's own ssh login plus sudo. No deploy user, no per-app keys.
- Database feature: next phase, not in the prototype.
- The prototype's server is a local Docker container with systemd (OrbStack). Never touch the real VPS.
- Ceiling: about 2,000 lines of shell excluding tests and the example apps.

## Test server contract (`test/server/`)

- `test/server/up.sh` builds and starts container `tando-testvm`, idempotent; `down.sh` removes it;
  `up.sh --reset` recreates it clean. When ready it writes `test/server/.ready`.
- Ubuntu (26.04 if the image exists, else 24.04), systemd as PID 1, sshd, sudo, Caddy, Node 24 (or the
  current LTS), rsync, curl, jq-free (the agent must not need jq). Native architecture is fine.
- User `vmadmin` with passwordless sudo, login by `test/server/id_test` (generated by `up.sh`, git-ignored).
- Published ports on 127.0.0.1 only: ssh `2222`, http `8080` (Caddy port 80). No other host ports.
- Caddy runs as a systemd service with a Caddyfile that listens on `:80` plain http (no TLS in the test).
- `docker restart tando-testvm` must bring systemd, sshd and Caddy back (used to test reboot recovery).
- Must not disturb the other containers on this machine (a local Supabase stack is running).

## Server layout (created by `tando host setup` and `tando up`)

```
/opt/tando/bin/tando-agent            root 755
/opt/tando/host.conf                  apps_domain, tls mode, port range
/opt/tando/apps/<app>/app.conf        root-owned registry: port, recipe, start, health, memory, jobs
/opt/tando/apps/<app>/incoming/       persistent upload dir, owned by the admin login (rsync deltas)
/opt/tando/apps/<app>/releases/<id>/  root-owned copy, read-only to the app
/opt/tando/apps/<app>/current         symlink, switched atomically (ln to temp name, mv -T)
/opt/tando/apps/<app>/shared/         app-writable data, survives releases
/opt/tando/apps/<app>/env             root:tando-<app> 640
/opt/tando/apps/<app>/state           key=value, written with temp file + mv
/opt/tando/apps/<app>/history.tsv     one line per deploy/rollback, with per-phase seconds
/etc/systemd/system/tando-<app>.service
/etc/caddy/tando/<app>.caddy          imported by the main Caddyfile
```

- Everything tando creates is prefixed `tando-`: system user `tando-<app>`, unit `tando-<app>.service`.
  App names match `^[a-z][a-z0-9-]{1,30}$`. The agent refuses anything it did not create.
- Ports are allocated by the server from a range in `host.conf` (default 4100-4199), never by the client.
- Release ids are assigned by the server: UTC `YYYYMMDD-HHMMSS`, with a suffix if it already exists.

## Pipeline

1. Client: read `tando.conf`, run `build` if set, stage `out` into `.tando/stage`, guard (no `.env*`,
   no symlinks leaving the tree, native `*.node` files must match the server's architecture).
2. Client: rsync delta into `incoming/` (must work with Apple's openrsync, protocol 29).
3. Client: `agent activate <app>`; the agent starts the activation as a detached transient unit
   (`systemd-run`, unique unit name, `--collect`, output to the journal) and returns the release id.
   The client then polls `agent deploy-status` and shows phases. A dropped ssh must not stop it.
4. Activation, holding an `flock` for the app only for its own duration:
   copy incoming to `releases/<id>` (no symlink following), fix ownership, **pre-flight**: start the new
   release as a transient unit on a spare port and health-check it; only then switch `current`, restart
   the real unit, health-check again through Caddy, mark the release `verified`, update `last_good`.
   Any failure after the switch rolls back to `last_good` and marks the release `bad`. A pre-flight
   failure never touches the running app.
5. Recovery: a boot oneshot unit and every mutating verb first run `recover`, which finishes or reverts
   an activation that was interrupted (state file says which phase).
6. Keep the newest 5 releases; never prune `last_good` or `current`.

`rollback` moves to the previous `verified` release and marks the one it left `bad`, so a second
`rollback` does not roll forward into it.

## Commands in the prototype

| Command | Notes |
|---|---|
| `tando host add <name> <user@host> [--port N] [--key path]`, `host ls`, `host setup <name>` | registry in `${TANDO_CONFIG_DIR:-~/.config/tando}`; setup installs the agent, the recover unit, the Caddy import |
| `tando init` | zero config: detect recipe (`node`, `static`; `next` standalone if time allows), write `tando.conf` |
| `tando up` | create the app on the server if missing (user, port, unit, Caddy site), then deploy; prints the link |
| `tando deploy`, `rollback [id]`, `releases` | as in Pipeline |
| `tando env set K=V ...`, `env unset K ...`, `env ls` | one restart per command; values that systemd's EnvironmentFile parser would alter are rejected or safely quoted; locked |
| `tando logs [-f] [-n N]` | journal of the app's unit only, `--no-pager` |
| `tando start`, `stop`, `restart` | |
| `tando ls [--watch N]` | boxed: host line (cpu, memory, disk, load) and one row per app |
| `tando status [app] [--watch N]` | boxed detail: version, uptime, memory against cap with bar, cpu, restarts, link, releases, recent deploys, sparkline of samples gathered while watching |
| `tando history [app]` | boxed table: when, release, result, total seconds, seconds per phase |
| `tando jobs` plus `job.<name> = <OnCalendar> | <command>` in `tando.conf` | scheduled jobs as systemd timers. `ExecStart` is always the fixed root-owned runner `/opt/tando/bin/tando-agent run-job <app> <name>`, running as the app user; the command text is never written into a unit file. Lower priority than everything above |

App-scoped commands take the app from `tando.conf` in the current directory or from `-a <app> -H <host>`.

## Link

`host.conf` has `apps_domain` and `tls` (`off`, `internal`, `auto`). The app is served at
`<app>.<apps_domain>`. In the test container: `apps_domain=localhost`, `tls=off`, so the link is
`http://<app>.localhost:8080` (curl resolves `*.localhost` to loopback).

## Unit template (hardening)

`User=tando-<app>`, `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`,
`PrivateDevices`, `ReadWritePaths=` the app's `shared/` only, `SocketBindAllow=` own port with
`SocketBindDeny=any` where the kernel supports it, `MemoryMax=` from config, `Restart=on-failure`,
`EnvironmentFile=`, `Environment=PORT=<port>`. Drop a directive only if it is proven not to work in the
test container, and say so in the report.

## Client and agent protocol

- The agent prints lines of `key=value` or tab-separated rows. The client parses with a fixed `case`
  whitelist and strips control characters. No `eval`, no `source` of anything from the server.
- One ssh master connection per host (ControlMaster) so status refreshes cost one round trip.
- The agent keeps nothing running between calls. A status call for all apps should stay under about
  50 ms of server CPU; read cgroup files and `systemctl show`, no per-app health request.

## UI library contract (`lib/ui.sh`)

Pure bash 3.2, no external commands in the render path except `tput`/`stty` once for size. Source it,
then call:

| Function | Behaviour |
|---|---|
| `ui_init` | detect width (COLUMNS, tput, default 80; cap 120), colour on only for a tty and when `NO_COLOR` is unset; ASCII borders when `TANDO_ASCII=1` or the locale is not UTF-8 |
| `ui_box_open "Title" ["right-side text"]`, `ui_box_line "text"`, `ui_box_sep ["label"]`, `ui_box_close ["footer"]` | a bordered box at the current width; lines are truncated with `…` using visible length (ANSI-aware) |
| `ui_kv "Key" "value"` | aligned key and value line inside a box |
| `ui_table "spec"` reading tab-separated rows on stdin, first row is the header | `spec` is comma-separated per column: `l` or `r` alignment, optional `:min-max` width, optional `!N` drop priority (higher drops first when the box is too narrow). Renders inside the open box |
| `ui_bar <value> <max> <width>` | prints a bar such as `████░░░░`, coloured green/yellow/red at 70% and 90% |
| `ui_spark "v1 v2 v3 ..."` | prints a sparkline `▁▂▃▅▇` |
| `ui_badge <state>` | coloured state word: `running`, `stopped`, `failed`, `deploying`, `verified`, `bad` |
| `ui_step <n> <total> "label" <state> ["detail"]` | one progress line for a deploy phase (`pending`, `run`, `ok`, `fail`), with seconds in detail |
| `ui_frame_begin`, `ui_frame_end` | for `--watch`: buffer a whole frame and repaint without flicker (cursor home, clear to end of screen); hide and restore the cursor; restore on exit or Ctrl-C |
| `ui_dur <seconds>`, `ui_bytes <bytes>` | `1m 31s`, `234 MB` |

The reference for look and technique is a sync script in another of the author's projects (not part of this repository)
(functions `ui_size` to `ui_spark`, about lines 170-330). No key handling: views are static, or
repainted by `--watch N`.

## Definition of done

`test/e2e.sh` passes from a clean `up.sh --reset`, covering at least:

1. `host setup`, `up` for `examples/hello`, link answers with version 1.
2. Change the app, `deploy`, link answers version 2; second upload transfers only the changed files.
3. Deploy a release that fails its health check: the running app never stops answering, the release is
   marked `bad`, `history` shows the failure.
4. `rollback` and `rollback` again behave as specified.
5. `env set` reaches the app, including a value with spaces, quotes and a backslash.
6. Kill the client's ssh during activation: the activation still finishes.
7. `docker restart tando-testvm` during activation: after boot the app serves a verified release.
8. `ls`, `status`, `history` render boxed output at 80 and 120 columns without a line exceeding the width.
9. A second app (`examples/site`) gets its own user, port and link, and cannot read the first app's `env`.
