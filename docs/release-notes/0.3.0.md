# tando 0.3.0

A server holds 100 apps and more, there is a dashboard on your laptop, and the monitoring looks at the
server, the apps and their databases the way a cloud console does. A few defaults changed: read
"Before you upgrade" and "Before you deploy database apps". The full list is in
[CHANGELOG.md](../../CHANGELOG.md).

## What is new

- **100 apps on one server** (tuned for 4 vCPU / 8 GB). App ports 4100-4999 (pre-flight ports
  14100-14999), user ids 30000-39999, one backup queue, jobs spread over a sixth of their period with
  a host-wide limit on runs at once, restarts that do not wait for each other, one systemd and Caddy
  reload for all apps, a memory check at deploy (`mem_overcommit`), `priority = high|low`, and
  `log_budget` shared by the apps' logs. `tando ls` above 50 apps shows a summary (`--all-rows` for
  every app).
- **PostgreSQL for many apps.** Sized from the server's RAM, with one pgbouncer (transaction
  pooling) in front for all apps. `db_pool` per app, `db_direct = true` to skip pgbouncer,
  `DATABASE_URL_DIRECT` for the release command.
- **Scale to zero.** `idle_stop = 6h` stops an app's web process after that long without a request;
  the next request starts it (about 0.1-0.3 s for a small app).
- **Database studio, always on.** One `tando-studio.service` per server; `tando db studio` mints a
  link and forwards a port, Ctrl-C ends only the forward.
- **The dashboard add-on** (a web app on your laptop, also in the Mac menu bar's "Open dashboard"):
  apps, deploys, logs, traffic, jobs, env, alerts, a cloud-style Server page, a Database tab, deploy,
  roll back, restart, stop/start and set variable with a confirmation, and the database studio in one
  click. Not in the main archive: `tando addon install dashboard`.
- **Monitoring.** Cloud-style host and app series (CPU steal and iowait, PSI, IOPS, network, TCP,
  throttling, OOM kills, tasks), the monitoring's own cost (new alert `monitor_cost`), database
  series and alerts (`db_deadlock`, `db_wrap`, `db_wrap_warn`), live views every 5 s
  (`tando status --follow`, `tando ls --follow`), `tando snapshot --json`, and `--json` for more
  commands.
- **Faster deploys and commands.** Fewer ssh calls per deploy, `restart`/`stop`/`start` return as
  soon as the server answers, `tando ls` of 100 apps in 0.1 s.
- `tando host rename <old> <new>`, and `tando host setup <host> --pg-stat-statements` for the top
  statements of each app's database.

## Before you upgrade

What changes on a server when `tando host setup` runs, so none of it is a surprise:

| Area | Before | Now |
|---|---|---|
| Journal cap of an app without `log_max` | min(2G, 5% of the disk) | min(256M, 5% of the disk, its share of `log_budget`); an over-cap journal is trimmed, oldest first |
| tandod `MemoryMax` | 64M | 160M (the unit is rewritten, tandod restarts) |
| App ports / pre-flight ports | 4100-4199, port + 100 | 4100-4999 / 14100-14999 (the old default range is widened) |
| User ids of new apps | 200-999 | 30000-39999 (existing apps keep theirs) |
| Backups | a timer per app at midnight | one queue, 01:00-05:00 server time, one at a time (`backup_window`, `backup_jobs`) |
| Start spread of jobs | 15 s | a sixth of the period, at most 10 minutes (`job_spread` sets it) |
| PostgreSQL | 20 connections, 32 MB shared buffers | sized from RAM; one pgbouncer on 127.0.0.1:6432 |
| Database studio | a program per ssh session | `tando-studio.service` (MemoryMax 128M) |

Steps:

1. Update tando on the laptop (`./install.sh --from tando-0.3.0.tar.gz`; the README has the details).
   An older laptop is told to update before it can open the studio.
2. Per server: `tando host setup <host>`. Apps keep their ports, users and settings; setup leaves running apps
   running; they still use their direct database URL until their next deploy. Check the output
   for the lines about PostgreSQL and the studio, and run `tando doctor <host>` afterwards.
3. If setup says PostgreSQL's new memory settings wait for a restart (a server whose apps already
   have databases): pick a quiet moment and run `tando host setup <host> --pg-restart`. It asks
   first; every app's database connections drop for a few seconds. Apps that reconnect on their own
   need nothing; others need a restart.
4. Optional: `tando host setup <host> --pg-stat-statements` (asks first: PostgreSQL restarts once)
   for the top statements in `tando snapshot` and the dashboard's Database tab.
5. Optional: `tando addon install dashboard`, then `tando dashboard`.
6. Check anything of yours on the server that listens on 4100-4999, 14100-14999 or 6432: tando's
   loopback rules keep app users off those ports, and a new app may be given a free one. Setup
   skips ports that are busy.
7. Check the log caps (`tando doctor` row "log caps") on a server with a small disk, and
   `backup_window` if your backups must run at another time.

## Before you deploy database apps

An app's `DATABASE_URL` points at pgbouncer from its next deploy (transaction pooling). Between two
transactions pgbouncer may give the app another server connection, so these do not work through it:

- `LISTEN` / `NOTIFY`, and session advisory locks (`pg_advisory_lock`; `pg_advisory_xact_lock` works),
- session `SET` (use `SET LOCAL` inside the transaction), temporary tables kept across transactions,
  `WITH HOLD` cursors,
- prepared statements by SQL (`PREPARE`), and protocol-level ones on a driver that needs
  pgbouncer 1.21+ (Ubuntu 24.04 has 1.22; with an older one turn them off in the driver, for
  example `prepareThreshold=0` in JDBC or `statement_cache_size=0` in asyncpg).

An app that needs one of these sets `db_direct = true` in tando.conf and deploys; it keeps
PostgreSQL itself. The release command (migrations) always gets the direct URL, as
`DATABASE_URL`. A rollback keeps the app's current `DATABASE_URL`. A deploy is refused when the apps'
`db_pool` (default 5 each) together would pass `max_connections` less 8: lower some pools or raise
`pg_max_connections` in `tando host setup`. `tando db` shows how an app connects. Details:
docs/COMMANDS.md, "Database connections and pgbouncer".

## Known limits

- The dashboard is for one laptop: it needs `tando` on the same machine, and Deploy is off for an app
  tando has no project folder for, or one another machine deployed last.
- `idle_stop` is not for static sites or containers; the first request after idle waits for the app
  to start.
- Backups that do not start before the window's end wait for the next night; widen `backup_window`
  or raise `backup_jobs` if `tando doctor` warns.
- Yarn and Bun workspaces and a Next.js package in a monorepo are still refused at deploy.
- Pre-1.0. Offsite backup is tested against a fake S3 only (see README).
