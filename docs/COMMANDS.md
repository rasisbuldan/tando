# tando command reference

Generated by hand on 14 Nov 2026 from `lib/help.txt` (the `flags:`, `args:`/`subs:` and `usage:`
lines that `lib/args.sh` enforces) and from the `# help:` headers and flag parsers of the plugins
(`lib/cmd-*.sh`). Checked with `bin/tando help`, `bin/tando <cmd> --help` and deliberate bad
flags (`TANDO_CONFIG_DIR` pointed at an empty temp dir, no server). When this file and
`lib/help.txt` disagree, help.txt is what the code enforces.

Conventions that apply to every command:

- App commands use `tando.conf` in the current directory, or name the app; `-H <host>` picks a server.
  **The app as a word:** it may follow a command, or its subcommand, that takes no word of its own
  there: `tando logs shop`, `tando restart shop`, `tando env ls shop`, `tando backup now shop`,
  `tando requests tail shop`, `tando domain ls shop`. Where a command has words of its own the app
  goes with `-a`: `env set|unset|import`, `backup restore|pull`, `domain add|rm`, `logs pull`.
  `rollback` takes an app and an id in either order (a release id such as `20261113-171442` is the
  id, any other word the app). `-a` works everywhere; `-a one` with the word `two` is refused.
  `tando env shop` (app before the subcommand) is refused with `tando env ls shop` suggested.
  Not for `deploy`/`up` (they upload the current directory) or server commands.
- Before the command name only `-a`, `-H`, `--json`, `--yes`, `--force`, `-h`/`--help` and
  `--version` are accepted. Anything else there is refused with exit 2 and the same command line
  with the command first (`tando -n 5 history` -> "-n goes after the command: tando history -n 5").
- `-h`/`--help` anywhere prints the command's help; the command does not run.
- Unknown flags, missing values, unknown subcommands and extra arguments: exit 2 with the usage.
  A mistyped command, flag or subcommand names the nearest one ("Did you mean --force?",
  `tando domain example.com` -> "tando domain add example.com"); a missing argument is named
  ("domain add needs <domain>").
  This check covers the commands with a section in help.txt. The plugins `go`, `next`, `link`,
  `open`, `ssh` and `cheat` have none, so their flags are not checked by args.sh (`go` checks its own).
- Exit codes: 0 ok, 1 failed, 2 usage error.

## Deploy

### init
`tando init [-H host] [--yes]`. Flags: `-H`, `--yes`. Arguments: none.
Writes `tando.conf` for the project here: detects the recipe (next, node, python, container,
static), start command and health path (`/api/health` or `/health` when the project defines that
route), and suggests `database = postgres` when `pg`/`postgres`/psycopg is a dependency. With one
server registered (or `-H`) it writes `host = <name>`. For Next.js it offers to add
`output: "standalone"` to next.config.*, or to write next.config.mjs when there is none (`--yes`
does it); declining does not fail init (tando.conf is written; deploy checks again).
Example: `tando init && cat tando.conf`

### up
`tando up [-H host] [--yes] [--force] [--wait]`. Arguments: none. `-a` is refused.
Creates the app on the server if needed, applies `tando.conf`, deploys. Writes `tando.conf` first
when there is none. The app is created only after the build succeeded. `--force`: deploy although
the app was last deployed from another directory. `--wait`: as for `deploy`.
Example: `cd my-app && tando up`

### deploy
`tando deploy [-a app] [-H host] [--force] [--yes] [--wait]`. Arguments: none.
Build here, upload changes, start the release on a spare port, health-check, switch, check again
through Caddy, then a soak (30 s, `soak = N`) in which a crash rolls back. Returns once live;
`--wait` (or `TANDO_WAIT=1`) waits for the soak. `--force`: another directory deployed last;
`--yes`: tando.conf now names another app or server than the last deploy from here.
When the upload and the settings are exactly those of the live, verified release, nothing is
activated: "already live", no new release, no restart (`tando restart` restarts it). A deploy that
finds another one's release soaking is queued and says what it waits for. While another deploy
(also from another terminal of the same user) is uploading, a deploy is refused at once.
Note: `-a` is accepted but not in the usage line (mismatch 8).
Example: `tando deploy`

### rollback
`tando rollback [app] [id] [-H host]`. Arguments: 0-2, in either order.
Back to the previous verified release, or to `<id>` (`tando releases` lists them).
Example: `tando rollback 20261113-171103`

### releases
`tando releases [app] [-H host] [--json]`. Arguments: 0-1 (the app).
Releases kept on the server, newest first, with state and age. Ids are UTC deploy times.
Example: `tando releases --json`

### history
`tando history [app] [-n N] [-H host] [--json]`. Flags also `-a`. Arguments: 0-1.
Deploys and rollbacks with result and phase times. Outside a project and without an app: every app
of the server.
Example: `tando history -n 10`

## Run

### status
`tando status [app] [--watch N] [-H host] [--json]`. Flags also `-a`. Arguments: 0-1.
One app in detail: state, release, memory, cpu, last 16 minutes, logs, alerts, its database
(`database  postgres  412 MB, 3 of 10 connections`: the size and the connections of its role
against the role's limit, as the alert checks last read them), backups, releases,
recent deploys. Outside a project without an app it shows `tando ls`. `--watch N` repaints.
Example: `tando status --watch 2`

### logs
`tando logs [app] [-f] [-n N] [--since T] [--until T] [--grep TEXT [-i] [--regex|-E]] [--level L] [--json]`
`tando logs --release ID | --deploy ID`
`tando logs pull <file> [--since T] [--until T]`
Flags: `-a -H -f -n --since --until --grep --regex -E -i --level --release --deploy --json`.
Arguments: 0-2 (`pull <file>`).
The app's stdout/stderr from its own journal namespace. `-n` defaults to 100. `--level
err|warning|notice|info|debug`. `--release ID`: lines from the time that release was live (for one
that never was: its deploy log). `--deploy ID`: that deploy's log and its start test. `pull` writes
to a local file. Note: `--until`, `--json` and `-E` are not in the usage lines (mismatch 6).
Example: `tando logs -f --grep error -i`

### start, stop, restart
`tando start|stop|restart [app] [-H host]`. Arguments: 0-1 (the app).
`start` starts a stopped app; `restart` restarts it; requests are held meanwhile. `stop` stops it:
visitors get 503 "<app> is stopped" until `start`; jobs stop too; nothing is removed.
Example: `tando restart -a shop`

### top
`tando top [host] [--watch N] [--read-only]`. Flags: `-H --watch --read-only`. Arguments: 0-1.
Full-screen dashboard of every registered server: apps, graphs, logs, history; start, stop,
restart and rollback from the keyboard unless `--read-only`. `--watch N` refresh (default 2 s).
`-n` does not exist (mismatch 3).
Example: `tando top --read-only`

## Configure

### env
`tando env ls [app] [--show]` · `tando env set KEY=VALUE ...` · `tando env set KEY` · `tando env unset KEY ...` ·
`tando env import [.env]`. Flags: `-a -H --show`. Subcommands: ls (default, 0-1: the app), set (1+), unset (1+),
import (0-1). `ls` hides the values (`******** (N characters)`); `--show` prints them.
Stored on the server (root, 640), never in the release. Before the first `tando up` the values are
staged on the server and applied when the app is created ("staged for <app>"). After a change the
app restarts once; a stopped app gets them at `tando start`, an app with nothing deployed at the
next deploy, a static site has no process. Values the app already has change nothing (no
restart). A running app is first started with the new values on its pre-flight port, beside the
live one (as a deploy does): if it does not come up healthy, nothing is changed or restarted and the
command exits 1 with the app's own words. If it passes there but then fails after the restart, the
previous env is put back and the app restarted on it (exit 1). An app that was not healthy before
keeps the new values (exit 1). `set`/`unset` restart the app once;
`set KEY` alone reads the value without echo (or from stdin). tando sets `PORT`, `HOME`,
`TANDO_DATA_DIR` (and `DATABASE_URL` with `database =`).
Example: `tando env set STRIPE_KEY`

### jobs
`tando jobs [ls [app]] [-H host]` · `tando jobs run <name> [-a app]`. Subcommands: ls (default,
0-1: the app), run (1: the job).
The app's scheduled jobs (`job.<name> = <schedule> | <command>` in tando.conf): schedule, next run,
last run and result. Not retried. `run` runs one now, as the app's user: its output, then
`job <name>: ok in Ns` or `failed (<result>, exit N)`; tando exits with the job's status.
A run that fails is alerted, by its timer or by hand alike: check `job.<name>`, one message per
failed run, resolved by the job's next success (so `tando jobs run <name>` after a fix clears it);
a job removed from tando.conf takes its alert with it (docs/MONITORING.md, "Scheduled jobs").
Jobs belong to a release: each release keeps the `job.` lines it was deployed with, and the
scheduled jobs are always those of the live release. A job added in a deploy is scheduled once
that release is verified (after its soak; `tando jobs` lists it from tando.conf before that, with
no next run), never when the release fails, and a rollback brings back the previous release's jobs.
Example: `tando jobs run nightly`

### db
`tando db psql [app]` · `tando db url [app] --show`. Flags: `-a -H --show`. Subcommands: psql, url (0-1: the app).
The app's PostgreSQL database (`database = postgres`). `url` refuses to print without `--show`.
Example: `tando db url --show`

### backup
`tando backup ls [app]` · `tando backup now [app]` · `tando backup restore <id> [--yes]` ·
`tando backup pull <id> <file>`. Flags: `-a -H --yes`. Subcommands: ls (default, 0-1), now (0-1), restore (1),
pull (2).
Backups of the data directory and database. `restore` asks first and keeps a safety backup. `ls`
and `pull` work for a destroyed app's final backup. `pull` creates the file mode 600 (it holds the
data and a database dump) and refuses an existing file. `ls` heads its time column `TIME (GMT)`.
`tando backup offsite [status|set|test|hosts|sync|off]` · `tando backup offsite key --show|--saved|--import|--rotate`:
copies of every backup in Cloudflare R2 or any S3-compatible store, encrypted on the server with a
recovery key shown once (docs/BACKUP.md). `set` asks for the account id or endpoint, bucket, access
key id and secret (no echo; or key=value lines on stdin) and checks them by writing, reading,
listing and deleting a test object before it saves anything. With offsite on, `ls` has a WHERE
column (`local`, `local + offsite`, `offsite only`, `local, uploading`, `local, upload failed`), and
`restore` and `pull` fetch an offsite-only backup first (verified).
Example: `tando backup pull 20261113-171815-manual backup.tar`

### restore
`tando restore <backup id> [-a app] [--yes]` · `tando restore --from-host <host id> [app...|--all] [--yes]`.
Flags: `-a -H --yes --from-host --all`.
The first form is `tando backup restore`. `--from-host` recreates the apps of another server (one
that is lost) on this one from the offsite bucket: runtimes, env (set on the server, never through
the laptop), settings, domains, then the newest backup's data and database. Releases are not in
backups: it prints the `tando up` to run in each project. Runbook: docs/BACKUP.md.
Example: `tando restore --from-host 3f9a01c2b7de --all -H newvps`

## Observe

### ls
`tando ls [-H host] [--all] [--watch N] [--json]`. Arguments: none. `-a` is refused.
The apps of a server: state, deploy age, memory, cpu, uptime, link (never cut: other columns are
dropped first at 80 columns). `--all`: every registered server, with `--watch` and `--json`.
Example: `tando ls --all`

### alerts
`tando alerts [--watch N]` · `enable` · `disable` · `test [name]` · `history [app] [-n N]` ·
`set [key=value ...]` · `silence <app|all> <30m|2h|1d|off>` ·
`notifier add <name> webhook|slack|telegram|ntfy|email` · `notifier rm <name>` · `notifier ls` ·
`heartbeat [off]`. Flags: `-a -H --watch -n`. Default subcommand: show.
What is firing on the server and where alerts go; checks run every minute (docs/MONITORING.md):
the apps (down, health, memory, disk, failed jobs as `job.<name>`, database connections as
`db_conns`, ...) and the host (disk, memory, Caddy, `postgres`, ...). `set` without arguments lists
every setting; `job=off`, `db_conns=off`, `postgres=off` turn the newest checks off, `db_conn_pct`
(80) and `db_conn_for` (5) are the connection threshold and its samples.
Secrets are read without echo. `notifiers` = `notifier` (mismatch 9).
Example: `tando alerts notifier add phone ntfy`

### health
`tando health [app] [--json]` · `tando health <app> --forget N`. Flags: `-a -H --json --forget`.
Uptime over 24 h and 7 d, incidents (start, how long, cause), probe latency; for one app also the
size and connections of its PostgreSQL database (as `tando status` shows them) and the
last lines it wrote before its last crash. Recorded once a minute by tando-watch (docs/MONITORING.md).
`--forget N` drops incident N of the app's list (1 is the newest) when it was a false alarm: the
line goes and its minutes are no longer counted in the uptime. An incident that is still open is refused.
Example: `tando health shop`

### errors
`tando errors [app] [--since 24h] [-n N] [--json]`. Flags: `-a -H --since --last -n --json`.
The app's error lines and stack traces (Node, Python, Go) grouped by type and first app frame: count,
last and first seen (GMT), the release it appeared in, one sample each (docs/MONITORING.md).
Example: `tando errors shop --since 6h`

### requests
`tando requests [summary [app]] [--since 15m|1h|24h]` · `tando requests tail [app] [-n N] [-f]` ·
`tando requests errors [app] [--since W] [--4xx]` (the app after the subcommand). Flags: `-a -H --last --since -n -f --4xx`.
Subcommands: summary (default), tail, errors.
The app's Caddy request log: counts, status codes, latency percentiles, slowest paths. `--last` =
`--since`.
Example: `tando requests errors --since 1h --4xx`

### audit
`tando audit [app] [-n N] [-H host]`. Flags also `-a`. Arguments: 0-1.
Who changed what on the server: one row per mutating action, with the sudo login and address.
Example: `tando audit -n 20`

## Servers

### host
`tando host add <name> <user@address> [--port N] [--key FILE] [--yes] [--force] [--no-check]`
`tando host setup <name> [apps_domain=D] [tls=auto|internal|off] [setting=value ...]`
`tando host ls` · `tando host rm <name>`
Flags: `--port --key --insecure-test --no-check --deploy --force --yes`. Subcommands: add (2),
ls (default, 0), setup (1+), rm (1).
`add` checks the login and shows the host key to trust (`--yes` trusts without asking,
`--no-check` saves without connecting, `--force` replaces an entry). `setup` installs rsync, curl,
nftables, Caddy, the firewall unit, timers and journals; safe to re-run. Settings: `apps_domain=`,
`tls=`, `public_port=`, `node=`, `python=yes`, `podman=yes`, `postgres=yes`, `swap=yes|no`,
`ufw=no`, `domain_tls=internal`; also `app_max_mb=`, `ci_max_mb=`, `ci_max_files=`,
`ci_max_file_mb=`, `unit_drop=`, `journal_max=` (not in help.txt), and the per-client limits on ports
80/443: `rate_limit=on|off|auto` (auto: on when tando owns Caddy), `conn_limit=N` (connections at
once per client address, IPv6 /64; default 200), `conn_rate=N` (new connections per second, burst
3x; default 100). Without `apps_domain`, links use
`<ip-with-dashes>.sslip.io` (an outside service). `--deploy` and `--insecure-test` are not in the
usage (mismatch 7). `care=on|off`: host care's security updates (on by default where tando
installed Caddy itself; docs/HOSTCARE.md).
Example: `tando host setup vps apps_domain=apps.example.com tls=auto`

`tando host status [name] [--json] [--watch N]` · `tando host care [name]` ·
`tando host care on [name] [--updates] [--reboot] [--window HH:MM-HH:MM] [--tz ZONE] [--lead MIN]
[--even-with-other-sites]` · `tando host care off [name] [--updates] [--reboot]` ·
`tando host care skip [name] [off]` · `tando host update [name] [--all] [--yes]` ·
`tando host reboot [name] [--now] [--yes] [--even-with-other-sites]`.
Subcommands: status (0-1), care (0-3), update (0-1), reboot (0-1). The name defaults to `-H`,
tando.conf or the only host. `status`: the machine, updates, security and health findings and a
to-do list (exit 1 when something fails); `care`: what tando may do by itself; `update`: install
the pending security updates (`--all`: every update); `reboot`: the safe reboot (docs/HOSTCARE.md).
Example: `tando host status vps`

### domain
`tando domain add <domain> [--www redirect|serve|off] [--wait] [--force] [-a app]` ·
`tando domain rm <domain> [-a app]` · `tando domain ls [app]`. Flags: `-a -H --www --wait
--force`. Subcommands: add (1), rm (1), ls (default, 0-1: the app).
`add` checks DNS from the laptop and prints the records to create when it does not point at the
server (`--wait` polls every 10 s for up to 30 min, `--force` skips), then adds the name to the
app's Caddy site (validated, rolled back if rejected) and waits up to 90 s for the certificate;
without one it says so, with the likely causes, and exits 1 (the domain stays added; `tando next`
lists it).
Example: `tando domain add example.com`

### doctor
`tando doctor [host]`. Flags: `-H`. Arguments: 0-1.
Checks a server end to end (connection, sudo, tando pieces and versions, Caddy, DNS, disk, memory,
timers, apps) and names the fix. Works on a server that is not set up yet.
Example: `tando doctor vps`

### version
`tando version [-H host]`. Client version and the server's agent version. `tando --version`
prints the client version only.
Example: `tando version -H vps`

## CI

### ci
`tando ci setup | rotate | ls | revoke <id|SHA256:...|all>`
`tando ci github [--ref TAG|SHA] [--repo URL] [--branch B] [--node N] [--env NAME] [--force]`
`tando ci hook [--branch B] [--force]` · `tando ci hook --remove`
Flags: `-a -H --ref --repo --branch --node --env --force --remove`. A subcommand is required.
Run by the admin in the app's directory. `setup` creates a deploy key for this app only and prints
the CI secrets once; `rotate` replaces every key; `github` writes `.github/workflows/deploy.yml`;
`hook` installs a git pre-push hook. See docs/CI.md. `--env` is not in help.txt's usage
(mismatch 5).
Example: `tando ci setup > ci-secrets.txt`

## More

### destroy
`tando destroy [app] [-H host] [--purge] [--yes]`. Arguments: 0-1 (the app).
Removes the app: unit, Caddy site, user, releases, data, database. A final backup is kept unless
`--purge`. Asks you to type the app name; `--yes` skips.
Example: `tando destroy -a old-app --purge`

### unlock
`tando unlock [app] [-H host]`. Clears the upload lease of a deploy whose terminal went away.
Example: `tando unlock`

### recipes
`tando recipes`. What `init` detects, how each recipe runs, what it needs on the server.
Example: `tando recipes`

### adopt
`tando adopt plan|apply <unit> [--health /path] [--no-jobs] [--yes]` ·
`tando adopt undo|status <app>` · `tando adopt site <app> [--apply]`. Flags:
`-H --health --no-jobs --yes --apply`. Subcommands: plan, apply, undo, status, site (1 argument
each). `-a` is refused.
Takes over a hand-deployed Next.js app (systemd unit behind Caddy) in place: `plan` is read-only,
`apply` backs up, switches and rolls back on failure, `undo` returns to the recorded state.
`site` shows what your own Caddy site lacks next to one tando renders: `lb_try_duration` in the
app's `reverse_proxy` (requests wait while the app restarts instead of getting 502) and the request
log that `tando requests`, `tando errors` and the 5xx alert read. `site --apply` adds them: a copy of
the Caddyfile is kept in `/var/backups/tando/<app>/`, the new file is validated, Caddy is reloaded
(never restarted) and the app is checked through it; a failure puts the previous file back. A site
it cannot read with certainty (several `reverse_proxy` lines to the port, a log of its own, an
imported file) is not edited: the lines to add by hand are printed.
See docs/MIGRATION.md.
Example: `tando adopt plan bakery -H vps --health /order/new`

### help
`tando help [command [subcommand]]`. Arguments: 0-3. The command list, or one command's help; words
after the command are accepted and show the same help (`tando help alerts notifier`).
Example: `tando help deploy`

## Limits and load

What keeps one app, or one client, from taking the server down. Per app in tando.conf, applied at
the next deploy; per host with `tando host setup <host> key=value`.

| Setting | Default | Limits | When it trips, a visitor or the app sees |
|---|---|---|---|
| `memory =` | 256M | each unit of the app; all its units together 3x | the process is killed (OOM) and restarted; node/next also get `NODE_OPTIONS=--max-old-space-size` at 70% so V8 exits instead of thrashing |
| `cpu =` | none | the app's units together (`50%` of a core, or `1.5` cores) | the app runs slower; neighbours keep their share |
| `tasks =` | 1024 | processes and threads of all its units | fork/thread creation fails in the app |
| `max_conns =` | 256 | Caddy's connections to the app | requests wait in Caddy for a free connection |
| `max_requests =` | none (off) | requests in flight through Caddy | over it a request waits up to the hold and then gets `503` "<app> is busy ..." with `Retry-After: 5` |
| `hold =` | 15, or `health_timeout` | seconds Caddy holds a request while the app (re)starts | after it the visitor gets 502; with `max_requests` also how long a request over the limit waits for its 503 |
| `stop_timeout =` | 10 | seconds a stopping process may finish its requests | it is killed (requests it still had fail); Caddy holds new ones meanwhile |
| host `conn_limit=` | 200 | connections at once per client address (IPv6: per /64) on ports 80/443 | further connections are reset |
| host `conn_rate=` | 100 | new connections a second per client address, burst 3x | further SYNs are dropped: the client retries a second later |
| host `rate_limit=` | auto | on, off, or auto: on only where tando owns Caddy (it installed it, or the Caddyfile has no other site) | `tando doctor` row "client limits" shows how often they tripped |

Loopback is never limited (tando's probes, an app calling itself through Caddy); ssh is not touched.
All apps together get half the CPU weight of the system services (Caddy, sshd, the agent), and an
app is the first thing the kernel kills when memory runs out. tando-watch restarts an app whose
unit runs but that does not answer (`liveness`, docs/MONITORING.md), never one that is only busy:
it asks the app's port directly first.
**Shedding is off by default.** Caddy 2.6 has one retry loop for "the app is full" and "the app is
restarting", so a request over `max_requests` gets its 503 only after the hold. With the 15 s hold
and clients that give up after 10 s, shedding turned a burst into timeouts (load test: 10,000
keep-alive connections to hello gave 3,400 rps with 1,700 timeouts with it, 5,560 rps and none
without). Set `max_requests` together with a short `hold` (2-3 s) for an app that starts in about a
second; a slow-starting app needs the long hold, and then shedding does not help.
**Per-request rate limits per app** (requests per second per client) need a Caddy plugin
(rate_limit) that the distribution's Caddy does not have: not offered. `max_requests` and the
per-client connection limits cover a flood; put a CDN or the plugin in front for more.
**Sizing:** max_conns about the number of requests the app can work on at once (a Node app: its
event loop answers many; a Python app with N workers: N to 2N); max_requests is the queue on top;
memory the app's peak, measured with `tando top` under load.
**Disk:** a deploy needs about 3x the release's size free (the upload in incoming/, the new
release, the kept ones), and as many free inodes as it has files; an upload over `app_max_mb`
(host setup) is refused before it is sent. **Caddy reloads:** `stop`, `start`, a domain change or
a new app reload Caddy's whole config; Caddy 2.6 finishes requests in flight but closes idle
keep-alive connections of every site it serves (clients reconnect; one that sends on a connection
being closed sees a reset). A deploy itself does not reload Caddy when the site did not change.
**Restarts under load:** an app that on SIGTERM only calls `server.close()` waits for every
keep-alive connection, and Caddy keeps its connections busy under load: the old process lives until
stop_timeout. Close idle connections too and answer with `Connection: close` from then on (see
examples/hello/server.js); Express and Fastify servers have the same `closeIdleConnections()`.

## Plugins (no help.txt section; flags not checked by args.sh)

### go
`tando go [user@address] [--domain D] [--www redirect|serve|off] [--dns wait|skip] [--name APP]
[--memory M] [--port N] [--key FILE] [--no-swap] [--free-link] [--ci] [--plain] [--yes] [--forget]
[apps_domain=D tls=... public_port=N domain_tls=... swap=... ufw=...]`
Setup wizard from an empty server to a live link over the real commands (host add, host setup,
init, up, domain add, alerts, ci). Nothing changes before the Run screen; answers are kept in
`$TANDO_CONFIG_DIR/go/` and resumed (`--forget` drops them). `--yes` takes every default; no
terminal gives numbered prompts (`--plain` forces them). `--insecure-test` is for test servers.
`tando go --help` shows the common flags (mismatch 4). A setting such as `public_port=N` that a
set-up server does not have yet adds `tando host setup` to the plan. See docs/EASE.md.
Example: `tando go root@203.0.113.7 --domain example.com --yes`

### next
`tando next [app] [-H host]`. Read-only, one ssh call: what you could do next on this app and
server, with the command.
Example: `tando next`

### link
`tando link [app]`. Prints the app's address (its own domain, else its link), for scripts.
Example: `curl -s "$(tando link)/api/health"`

### open
`tando open [app]`. Opens the app in the browser (macOS `open`, else `xdg-open` with a display);
prints the address otherwise or with `TANDO_NO_BROWSER=1`.
Example: `tando open`

### ssh
`tando ssh` · `tando ssh <app>` · `tando ssh <app> -- <command>` · `tando ssh -- <command>`.
Without an app: your own login shell on the server. With an app: a shell as the app's user in its
sandbox (its env loaded, cwd its current release, only shared/ writable; agent verb `shell`), or
one command there with `-- <command>` (its exit status is tando's). `tando ssh -- <command>` uses
the app of tando.conf here. An interactive shell needs a terminal; without one tando says to use
`-- <command>`. Refused with a CI deploy key.
Example: `tando ssh shop -- node scripts/migrate.js`

### cheat
`tando cheat`. The commands that matter on one screen. No server call.
Example: `tando cheat`
