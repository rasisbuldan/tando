# tando command reference

Generated by hand on 14 Nov 2026 from `lib/help.txt` (the `flags:`, `args:`/`subs:` and `usage:`
lines that `lib/args.sh` enforces) and from the `# help:` headers and flag parsers of the plugins
(`lib/cmd-*.sh`). Checked with `bin/tando help`, `bin/tando <cmd> --help` and deliberate bad
flags (`TANDO_CONFIG_DIR` pointed at an empty temp dir, no server). When this file and
`lib/help.txt` disagree, help.txt is what the code enforces.

Conventions that apply to every command:

- App commands use `tando.conf` in the current directory, or name the app; `-H <host>` picks a server.
  **The app as a word:** it may follow a command, or its subcommand, that takes no word of its own
  there: `tando logs shop`, `tando restart shop`, `tando env ls shop`, `tando backup now shop`,
  `tando requests tail shop`, `tando domain ls shop`. Where a command has words of its own the app
  goes with `-a`: `env set|unset|import`, `backup restore|pull`, `domain add|rm`, `logs pull`.
  `rollback` takes an app and an id in either order (a release id such as `20261113-171442` is the
  id, any other word the app). `-a` works everywhere; `-a one` with the word `two` is refused.
  `tando env shop` (app before the subcommand) is refused with `tando env ls shop` suggested.
  Not for `deploy`/`up` (they upload the current directory) or server commands.
- Before the command name only `-a`, `-H`, `--json`, `--yes`, `--force`, `-h`/`--help` and
  `--version` are accepted. Anything else there is refused with exit 2 and the same command line
  with the command first (`tando -n 5 history` -> "-n goes after the command: tando history -n 5").
- `-h`/`--help` anywhere prints the command's help; the command does not run.
- Unknown flags, missing values, unknown subcommands and extra arguments: exit 2 with the usage.
  A mistyped command, flag or subcommand names the nearest one ("Did you mean --force?",
  `tando domain example.com` -> "tando domain add example.com"); a missing argument is named
  ("domain add needs <domain>").
  This check covers the commands with a section in help.txt. The plugins `go`, `next`, `link`,
  `open`, `ssh` and `cheat` have none, so their flags are not checked by args.sh (`go` checks its own).
- Exit codes: 0 ok, 1 failed, 2 usage error.
- Every `tando.conf` setting: [docs/CONFIG.md](CONFIG.md), or `tando help conf`.

## Deploy

### init
`tando init [-H host] [--yes]`. Flags: `-H`, `--yes`. Arguments: none.
Writes `tando.conf` for the project here: detects the recipe (next, node, python, container,
static), start command and health path (`/api/health` or `/health` when the project defines that
route), and suggests `database = postgres` when `pg`/`postgres`/psycopg is a dependency. With one
server registered (or `-H`) it writes `host = <name>`. For Next.js it offers to add
`output: "standalone"` to next.config.*, or to write next.config.mjs when there is none (`--yes`
does it, and prints the lines it added with their numbers); declining does not fail init
(tando.conf is written; deploy checks again).
Example: `tando init && cat tando.conf`

### up
`tando up [-H host] [--yes] [--force] [--wait]`. Arguments: none. `-a` is refused.
Creates the app on the server if needed, applies `tando.conf`, deploys. Writes `tando.conf` first
when there is none. The app is created only after the build succeeded. `--force`: deploy although
the app was last deployed from another directory. `--wait`: as for `deploy`.
Example: `cd my-app && tando up`

### deploy
`tando deploy [-a app] [-H host] [--force] [--yes] [--wait] [--dry-run]`. Arguments: none.
Build here, upload changes, start the release on a spare port, health-check, switch, check again
through Caddy, then a soak (30 s, `soak = N`) in which a crash rolls back. Returns once live;
`--wait` (or `TANDO_WAIT=1`) waits for the soak. `--force`: another directory deployed last;
`--yes`: tando.conf now names another app or server than the last deploy from here.
When the upload and the settings are exactly those of the live, verified release, nothing is
activated: "already live", no new release, no restart (`tando restart` restarts it). A deploy that
finds another one's release soaking is queued and says what it waits for. While another deploy
(also from another terminal of the same user) is uploading, a deploy is refused at once.
`release = <command>` in tando.conf runs once per deploy on the server, between pre-flight and
switch (database migrations): see [The release command](#the-release-command).
`--dry-run`: build and stage here, swap the platform packages, then print the file count, the
size, the five largest directories and each swapped package with whether it was verified against
the lockfile. Nothing is uploaded: no lease, no configure, no runtime install, no release; the
server is only asked for its platform and whether the app exists (`configure check`). An app that
does not exist yet is staged all the same (`tando up` creates it). The last deploy target of the
directory is not changed.
A fresh clone (dependencies in package.json, no node_modules) stops before anything else with the
lockfile's install command (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install
--frozen-lockfile`, `bun install --frozen-lockfile`); `tando up` and the pre-push hook run it.
Output: the stage line shows the files and the size; each swapped npm package is one line (yellow
when not verified; docs/CROSS-ARCH.md); a release over 50 MB names its three largest directories.
Outside a terminal (CI, a log file) every step prints a line when it starts.
Note: `-a` is accepted but not in the usage line (docs/DEV-NOTES.md, mismatch 8).
Example: `tando deploy`

### rollback
`tando rollback [app] [id] [-H host]`. Arguments: 0-2, in either order.
Back to the previous verified release, or to `<id>` (`tando releases` lists them).
A stopped app (`tando stop`) is treated as a deploy to it is: when the release rolled back to passes
its health check it goes live and the app runs; when it fails, the app is left as it was: its
release, stopped.
Example: `tando rollback 20261113-171103`

### releases
`tando releases [app] [-H host] [--json]`. Arguments: 0-1 (the app).
Releases kept on the server, newest first, with state and age. Ids are UTC deploy times.
Example: `tando releases --json`

### history
`tando history [app] [-n N] [-H host] [--json]`. Flags also `-a`. Arguments: 0-1.
Deploys and rollbacks with result and phase times. Outside a project and without an app: every app
of the server. `RELCMD` is the time of the release command, shown when a listed deploy ran one
(`release_s` in `--json`).
Example: `tando history -n 10`

## Run

### status
`tando status [app] [--watch N | --follow] [-H host] [--json] [--check]`. Flags also `-a`. Arguments: 0-1.
One app in detail: state, release, memory, cpu (the last minute: `12%  last minute`), last 16 minutes, logs, alerts, its database
(`database  postgres  412 MB, 3 of 10 connections`: the size and the connections of its role
against the role's limit, as the alert checks last read them), backups, releases,
recent deploys. The backup line turns red (`over 50 h, the backup alert fires`) past the backup
alert's `backup_hours`, the same threshold. Each worker (`worker.<name>` in tando.conf) has a line: `worker  queue  running
restarts 0  memory 41 MB of 256 MB`; `restarting` when it exited and waits to be started again.
Outside a project without an app it shows `tando ls`. `--watch N` repaints; the footer says how
old the data is (`updated 2s ago`), and a refresh that fails or gets no answer within 15 s marks
the screen: a red `not answering: <why>` line and `STALE: data 40s old, reconnecting` (the same
in `tando ls`, `tando alerts` and `tando host status` with `--watch`).
`--follow`: live, every 5 s, over one ssh session that stays open: the server pushes a frame
(tandod's 5 s loop: state, memory, cpu over the last 5 s, restarts, load; the whole status once a
minute and at once when an app changes state; docs/MONITORING.md, "Live views"). The footer says
`live · updated 2s ago`; the cpu line says `last 5 s`. A server that cannot push (an older one,
tandod not running, no cgroup v2) is asked every 5 s instead, as `--watch 5`. Also `tando ls --follow`.
Example: `tando status --watch 2`, `tando status web --follow`

### logs
`tando logs [app] [-f] [-n N] [--since T] [--until T] [--grep TEXT [-i] [--regex|-E]] [--level L] [--worker NAME] [--json]`
`tando logs --release ID | --deploy ID`
`tando logs pull <file> [--since T] [--until T]`
Flags: `-a -H -f -n --since --until --grep --regex -E -i --level --release --deploy --worker --json`.
Arguments: 0-2 (`pull <file>`).
The app's stdout/stderr from its own journal namespace. `-n` defaults to 100. `--level
err|warning|notice|info|debug`. `--release ID`: lines from the time that release was live (for one
that never was: its deploy log). `--deploy ID`: that deploy's log and its start test. The app's
output includes its jobs' and workers'; `--worker NAME` shows one worker's only. `pull` writes
to a local file. Note: `--until`, `--json` and `-E` are not in the usage lines (docs/DEV-NOTES.md, mismatch 6).
Example: `tando logs -f --grep error -i`

### start, stop, restart
`tando start|stop|restart [app] [-H host]`. Arguments: 0-1 (the app).
`start` starts a stopped app; `restart` restarts it; requests are held meanwhile. `stop` stops it:
visitors get 503 "<app> is stopped" until `start`; jobs and workers stop too (a worker gets its
`worker.<name>.stop_timeout` to finish); nothing is removed. `start` and `restart` start the
workers again, and so does `tando env set` (with the new env).
Before an app's first release is live (a first `up` still running, or one that failed and left
nothing live) its address answers 503 "<app> is being deployed" with `Retry-After: 10`, not 502.
Example: `tando restart -a shop`

### top
`tando top [host] [--watch N] [--read-only]`. Flags: `-H --watch --read-only`. Arguments: 0-1.
Full-screen dashboard of every registered server: apps, graphs, logs, history; start, stop,
restart and rollback from the keyboard unless `--read-only`. Live by default: one ssh session per
server for the whole session, the server pushing the status every 5 s (`tando status --follow`);
releases, history and metrics of the selected app are still asked for, at most every 10 s. A server
that cannot push (older, no tandod, no cgroup v2) is asked every 2 s. `--watch N`: ask every N
seconds instead of following (the previous behaviour).
`-n` does not exist (docs/DEV-NOTES.md, mismatch 3).
Example: `tando top --read-only`

## Configure

### env
`tando env ls [app] [--show | --names] [--json]` · `tando env set KEY=VALUE ...` · `tando env set KEY` · `tando env unset KEY ...` ·
`tando env import [.env]` · `tando env log [n]`; `--note "text"` on set, unset and import. Flags:
`-a -H --show --names --note --json`. Subcommands: ls (default, 0-1: the app), set (1+), unset (1+),
import (0-1), log (0-1). `ls` hides the values (`******** (N characters)`); `--show` prints them.
`ls --names`, and `ls --json` always, read the names only through the agent's `env-names` (no
value leaves the server; not audited as a reveal, as `env-ls` is; a deploy key is refused it):
`{"host", "app", "names": ["KEY", ...]}`.
Stored on the server (root, 640), never in the release. Before the first `tando up` the values are
staged on the server and applied when the app is created ("staged for <app>"). After a change the
app restarts once; a stopped app gets them at `tando start`, an app with nothing deployed at the
next deploy, a static site has no process. Values the app already has change nothing (no
restart). A running app is first started with the new values on its pre-flight port, beside the
live one (as a deploy does): if it does not come up healthy, nothing is changed or restarted and the
command exits 1 with the app's own words. If it passes there but then fails after the restart, the
previous env is put back and the app restarted on it (exit 1). An app that was not healthy before
keeps the new values (exit 1). `set`/`unset` restart the app once;
`set KEY` alone reads the value without echo (or from stdin). tando sets `PORT`, `HOME`,
`TANDO_DATA_DIR` (and `DATABASE_URL` with `database =`).

`env log`: the env changelog, key names only. Every change adds one entry to
`/opt/tando/apps/<app>/env.log` on the server (root 600, written whole and renamed like the env
file; the newest 200 are kept; `tando destroy` removes it): time, who (as in the audit log), verb
(`set`, `unset`, `import`, `database`), the note, and the names added, changed and removed. It never
holds a value, a length or a hash of one. A change that alters nothing, and one the health check
put back, write nothing. `--note "text"` is one line of at most 200 characters (control characters
are refused); without it the list shows "set 2 keys" or "removed 1 key". `tando env log` prints one
row per entry, newest first: `[2026-11-20 14:02] [the note] >` (UTC). At a terminal the rows are
numbered, you give a number (Enter alone: the newest) and the entry's page opens, as `tando db
studio` picks an app; piped, it only prints. `tando env log 3` opens entry 3 (1 is the newest, so
the number changes as entries are added). `--json` prints the entries (names only). Whoever may
`env ls` may read it (the admin's login); a CI deploy key is refused by the gate.
```
tando env log
[2026-11-20 14:02] [removed 1 key] >
[2026-11-19 09:30] [rotated the payment keys] >
```
Example: `tando env set STRIPE_KEY`

### jobs
`tando jobs [ls [app]] [-H host] [--json]` · `tando jobs run <name> [-a app]` · `tando jobs log <name> [-n N]` ·
`tando jobs pause <name>` · `tando jobs resume <name>`. Subcommands: ls (default, 0-1: the app),
run, log, pause, resume (1: the job; the app with `-a`).
The app's scheduled jobs (`job.<name> = <schedule> | <command>` in tando.conf). `ls` shows per job
the schedule (as written), the next run, the last run and how it ended (`ok`, `exit 3`, `timed
out`, `killed (memory)`, `killed (SEGV)`), how long it took, and the command; under the table the
next three run times of each job by the server's clock, with its time zone, so a wrong schedule
shows before it has missed anything. A paused job shows `paused`. Not retried (see below).
`--json`: `{"host", "app", "zone", "zone_name", "jobs": [{"name", "schedule", "state" (on, paused,
running), "next_run", "last_run" (epoch), "result", "exit_code", "duration_s", "command",
"next_runs" (the next three, server time, "2026-11-21 09:00")}]}`.
`run` runs one now, as the app's user: its output, then `job <name>: ok in Ns` or `failed
(<result>, exit N)`; tando exits with the job's status (124 when it timed out).
`log` shows the output of the last N runs (default 3, at most 50), each under its time, result and
duration, the last 200 lines of each. A run's lines are found in the journal by a cursor taken
before it started, never by time or by systemd's invocation id; a run the journal has already
rotated away says so. Job output is not copied anywhere else.
`pause` switches the job's timer off and `resume` on, without editing tando.conf or deploying. The
pause is kept on the server, so a deploy, a rollback, a recovery and a reboot leave the job off; a
run already going on finishes, `tando jobs run` still works, and a resume does not run what was missed
while it was paused (the next run is the next time). A job removed from tando.conf
loses its pause (added again, it runs). CI deploy keys cannot run `jobs`, `log`, `pause` or
`resume` (the gate allows its few read verbs and the deploy; nothing was added).

Schedules. Either cron or systemd:
- cron: five fields (minute hour day-of-month month weekday) with `*`, lists (`1,15`), ranges
  (`mon-fri`, `9-17`), steps (`*/15`, `10-50/10`), month names (`jan`) and weekday names (`mon`;
  0 and 7 are Sunday), or `@hourly @daily @midnight @weekly @monthly @yearly @annually`. It is
  translated to systemd's calendar text on your machine before anything is sent
  (`*/15 * * * *` is `*-*-* *:00/15:00`), only when both mean exactly the same; `tando jobs` shows
  what you wrote. Refused, with what to write instead: both day of month and weekday set (cron
  runs on either, systemd only when both match: use two jobs), `5/15` (write `5-59/15`), ranges
  that wrap (`22-3`: write `22-23,0-3`), `@reboot`, the `?` `L` `W` `#` of other schedulers, a
  sixth field (seconds, year) and values out of range. A weekday-only or day-only schedule with a
  `*/n` in the other field keeps cron's meaning (both must match).
- systemd: `daily`, `hourly`, `*-*-* 03:00`, `Mon..Fri 09:00`, `*:0/10`; `man systemd.time`.
  Checked by the server before the deploy starts (`tando up`, `deploy --dry-run` and `configure
  check` all refuse a bad one, naming the job). A zone can be written in it (`*-*-* 03:00 UTC`).
All times are the server's time zone (`tando jobs` names it; most servers use UTC), whatever your
machine's.

How runs behave.
- A job still running when its next time comes is not started a second time: systemd starts a
  oneshot unit only once at a time, and the time that was missed is simply not run, not even when
  that run ends (the job's start condition skips a time that passed during its last run; it needs
  systemd 250 or later, as on Ubuntu 24.04; `e2e-jobs` J7).
- A job removed from tando.conf (or gone with a rollback) loses its timer at once; a run of it still
  going on finishes within its timeout, then its unit is removed.
- A run the server missed because it was off or down is made up once when it is back
  (`job_missed = run`, the default: systemd's `Persistent=`); `job_missed = skip` waits for the
  next time. A deploy does not make up a run, and neither does `tando jobs resume`.
- A job's start is spread over `job_spread` seconds (default: a sixth of its period, at most 10
  minutes; `RandomizedDelaySec=` with `FixedRandomDelay=yes`, so each timer keeps its own offset),
  so the hourly jobs of many apps do not start together; `job_spread = 0` starts them on the second.
  At most `job_slots` job runs go on at once on the server (all apps; host setup, default the
  number of CPUs, at least 2): a run waits for a slot before it starts, and the wait counts in its
  timeout. A
  job's `job.<name>.spread` and `.missed` set one job.
- The last 50 runs of each job (start, result, duration, exit status; never output) are kept on the
  server (`jobhist/` in the app's directory, root only), so `ls` answers after the journal has
  rotated or the host has restarted.
A run is stopped after its timeout: `job_timeout = <seconds>` for all of the app's jobs (1 to
86400; default 3600, one hour) or `job.<name>.timeout = <seconds>` for one. Past it systemd stops
the job (SIGTERM, SIGKILL 90 s later) and records the result `timeout`: `tando jobs` shows it,
`run` says `timed out`, and the alert fires like for any failed run. A job that hangs therefore
ends and is alerted instead of running for ever. A job killed at the app's memory limit shows
`killed (memory)`.
Each job runs in its own units, `tando-<app>_job-<name>.service` and `.timer` (`_` is in no app or
job name, so the name is exactly this app's job; before this change they were `tando-<app>-job-<name>`,
which app `foo-job` shared with app `foo`: `tando host setup` renames them, keeping each timer's
last run).
A run that fails is alerted, by its timer or by hand alike: check `job.<name>`, one message per
failed run, resolved by the job's next success (so `tando jobs run <name>` after a fix clears it);
a job removed from tando.conf takes its alert with it (docs/MONITORING.md, "Scheduled jobs"). A
failing job also shows in `tando ls` (alerts firing) and `tando status` (the alert row).
Jobs belong to a release: each release keeps the `job.` lines it was deployed with, and the
scheduled jobs are always those of the live release (its code, its settings and env). A job added in
a deploy is scheduled once that release is verified (after its soak; `tando jobs` lists it from
tando.conf before that, with no next run), never when the release fails, and a rollback brings back
the previous release's jobs. Not done: a retry of a failed run (`retries =`).
Example: `tando jobs run nightly` · `tando jobs log nightly -n 5` · `tando jobs pause nightly`

### db
`tando db [info] [app]` · `tando db psql [app]` · `tando db url [app] --show` ·
`tando db studio [app] [--no-open] [--json] [--idle M] [--stop]`. Flags: `-a -H --show --no-open --json --idle --stop`.
Subcommands: info (default, 0-1: the app), psql, url, studio (0-1).
The app's PostgreSQL database (`database = postgres`). Without a subcommand: its size, the
connections in use and the limits of its role as PostgreSQL holds them. `url` refuses to print
without `--show`. See "Database limits" and "Upgrading PostgreSQL" below.
Example: `tando db url --show`

#### tando db studio
A small web page for the app's database, in your browser: the tables and views with their
estimated rows and sizes (a filter box), a table's rows (pages of 50, 100 or 500, sort by a column,
NULL and `''` told apart, a long or JSON or bytea value opens in a side panel) and its structure
(columns, indexes, "Open in SQL"), and a SQL editor (Cmd/Ctrl+Enter runs the selection or the
statement at the cursor, Shift added runs everything, Cmd/Ctrl+. cancels; one result tab per
statement, the error's position selected in the editor, notices, CSV download). Light and dark.

- **Always on, one per server** (docs/STUDIO.md). Host setup installs `tando-studio.service`; it
  holds nothing while nobody uses it (no database connection, a few MB). The command mints a link
  for you and forwards a port to the service; Ctrl-C ends the forward, never the studio. The page
  has a list of the server's apps with a database: picking one opens it (each request names its
  app; each app is served by its own process, as that app's user, with that app's role).
- **Which app the link opens.** The app named
  (`tando db studio shop`, `-a shop`), else the project's (tando.conf), else you pick it:
  outside a project the command lists the apps of the server that have a database (size, state;
  the others dimmed as "no database") and asks for a number; with exactly one it opens that one and
  says which; without a terminal it prints the list with the command for each and exits 2. The page
  names the app, its database and the server in its top bar and title. The sidebar lists this database's own schemas, never PostgreSQL's (pg_catalog,
  information_schema, pg_toast). The app's role can connect to no database but its own (no CONNECT
  for PUBLIC on any app database, set again at every deploy and host setup).
- **Only the app's own tables.** A statement that reads a system table or view (`pg_class`,
  `pg_roles`, `pg_stat_activity`, `pg_database`, `information_schema.tables`, ...) is refused
  before it runs, by any route: written plainly or quoted, inside a CTE, subquery, `EXISTS`,
  `UNION` or `LATERAL`, through a view of the app's, after `SET search_path`, or inside an
  `EXPLAIN`; browsing such a view's rows is refused the same way. So are functions that read the catalogs or the server's state (`pg_*` ones,
  `current_setting`, `has_table_privilege`, `obj_description`, `to_regclass`, `txid_*`, `lo_*`,
  ...), casts to `regclass` and its kin (`tableoid::regclass` too), and `SHOW ALL` (`SHOW work_mem`
  is fine). The message names what was refused: `the studio only reads this app's own tables:
  pg_catalog.pg_authid is a system table`. Everyday functions stay: `now()`, `current_user`,
  `version()`, aggregates, string, date and JSON functions, `generate_series`, `pg_typeof`,
  `pg_size_pretty`, `pg_sleep`, the advisory locks, the app's own functions. It works by the
  server's own plan of each statement (one extra round trip, about 0.3 ms) and by names: a
  function the app defined that reads a catalog inside is not seen, and an app column or table
  whose name starts with `pg_` is refused too. `tando db psql` reads everything the role can.

- **Read-only.** Each run is one read-only transaction, opened with a snapshot before any of your
  statements (so `SET TRANSACTION READ WRITE` cannot turn it around) and always rolled back, then
  the session is reset (`DISCARD ALL`). Only statements that start with `SELECT`, `WITH`, `VALUES`,
  `TABLE`, `SHOW`, `EXPLAIN`, `SET` or `RESET` are sent (not `SET TRANSACTION`, `SET ROLE`,
  `SET SESSION ...`); anything else is refused before it runs: writes, DDL, `LOCK`, `VACUUM`,
  `ANALYZE`, `COPY`, `COMMIT`, `CALL`, `DO`, `NOTIFY`. **Writes stay in `tando db psql`.**
- **Limits.** A statement stops after 30 s (the studio's own clock: `SET statement_timeout = 0`
  does not lift it); 1,000 rows kept per statement (100 or 10,000 to choose), a cell cut at 64 KB
  (16 KB when browsing a table), 8 MB of data per answer; at most 100 statements and 256 KB of SQL
  per run; one request at a time (the page waits for a running query, or Cancel stops it).
- **It does not crowd out the apps.** The studio's database process is held to 2 MB per sort or
  hash before it spills to a temporary file (`work_mem`, `hash_mem_multiplier` 1), one process (no
  parallel workers), no JIT, temporary files within the role's `db_temp_limit` (1 GB); these
  cannot be changed from the editor (`SET` of them and `set_config` are refused); one value a
  query builds (`repeat`, `string_agg`) can still take up to 1 GB while the query runs. The agent checks
  that the process is this app's studio session, then moves it into a cgroup of its own at CPU
  and I/O weight 1 (the apps and PostgreSQL have 100: on a busy CPU it gets about 1%, on an idle
  one all of it), at nice 19 and, where the disk's I/O scheduler has classes, the idle I/O class.
  It never gets a memory limit: the kernel killing a PostgreSQL process makes the server restart
  every app's sessions; the settings are the bound for sorts and hashes. It waits at most 2 s for a
  lock; a statement stops at 30 s in the editor and 10 s when browsing (so an app's migration waits
  for a studio query at most that long); nothing stays open between two requests (no transaction,
  no snapshot); its connection closes after 60 s unused, and it does not connect when the app would
  have fewer than 2 of its role's connections left (or the server fewer than 2 of all). Numbers:
  bench/RESULTS.md "db studio".
- **What it can still do** as the app's role: read the app's tables and views; use CPU and disk
  for up to 30 s per statement; hold a lock that delays the app's migration for that long; take an
  advisory lock (released when the run ends); call the app's own functions, whatever they do
  inside. None of this is beyond `tando db psql`.
- **How it is reached.** The server listens on no network port: each admin login has its own
  unix socket, `/run/tando-studio/u/<login>/s` (0600, that login's), and this command's own ssh
  connection forwards `127.0.0.1:<port>` on your computer to it (a stable port per server between
  47100 and 47409; the next free one when it is taken). The link it prints works once, within a
  minute, on that port only: the page trades its code for a key it keeps for the tab (a reload
  keeps working). The database password never leaves the server.
- **When it stops.** The forward: Ctrl-C in the terminal. A session (the page's key): Stop in the
  page, 12 hours unused, `tando db studio --stop` (it restarts the service: every key of every
  admin ends), a host setup. An app's process in the studio ends after 2 minutes without a request,
  its database connection after 60 s. The page shows "This studio session ended"; your editor
  text is kept.
- **For programs: `--json`.** No browser and no box: one line `{"url":"http://127.0.0.1:<port>/#c=<code>&app=<app>","port":<port>,"sid":"<word>"}`
  on stdout when the forward answers, and the forward ends when the command's stdin reaches EOF
  (the program that started it closed the pipe or died), as Ctrl-C would. Against the always-on
  studio, a line `mint <app>` on stdin prints one more such line on the same port with a fresh
  code for that app (`{"error":"..."}` when it cannot), so one forward serves many links. The
  dashboard add-on runs it so (addons/dashboard/docs/SPEC.md "Database studio").
- **Older servers.** Against a server set up by an older tando the command starts that server's
  per-session studio as before (`--idle M`, one app per studio). An older tando against a newer
  server is told to update.
- **History** of your queries (the last 100) and the editor's text stay in the browser, encrypted
  (AES-GCM with a key the studio derives from the role's password: nothing else on the computer
  can read them, not even a later page on the same port). They are per app and port, so a second
  studio of the same app at the same time has its own.
- **sshd** must allow forwarding to a unix socket for your login (the default:
  `AllowStreamLocalForwarding yes`). When it does not, the command says so and what to add.
- At most 2 processes per app and 4 in all serve the studio at once (one per page and app; the
  one unused longest gives way). CI deploy keys cannot open it (the client, the gate, sudo and
  sshd each refuse). The audit log (`tando audit`) has every link minted (who, which app and
  port), never a statement.

Example: `tando db studio shop`

### backup
`tando backup ls [app] [--json]` · `tando backup now [app]` · `tando backup restore <id> [--yes]` ·
`tando backup pull <id> <file>`. Flags: `-a -H --yes`. Subcommands: ls (default, 0-1), now (0-1), restore (1),
pull (2).
Backups of the data directory and database. `restore` asks first and keeps a safety backup. `ls`
and `pull` work for a destroyed app's final backup. `pull` creates the file mode 600 (it holds the
data and a database dump) and refuses an existing file. `ls` heads its time column `TIME (GMT)`.
`ls --json`: `{"host", "app", "backups": [{"id", "kind", "created", "size_bytes", "holds",
"where"}], "offsite_error"}` (`where`: local, both, offsite, local+pending, local+uploading,
local+failed; null without offsite).
A restore of an app stopped with `tando stop` leaves it stopped (the data restored; `tando start`
starts it). A restore cut off by a kill or a reboot is ended by the server's recovery: the app runs
its release again (a stopped app stays stopped). When the database (or an adopted app's data directory) was being replaced at that moment,
it may be partly restored: `tando status <app>` and `tando doctor` say so, with the backup to restore
again and the safety backup that holds the data from before (`tando ls` marks the app), until a restore ends.
`backup now` runs to its end when the ssh session drops (Ctrl-C). A backup cut off by a kill or a
reboot leaves an unfinished temporary directory: `tando doctor` names it, and the next backup of the
app or the server's recovery removes it.
`tando backup offsite [status|set|test|hosts|sync|off]` · `tando backup offsite key --show|--saved|--import|--rotate`:
copies of every backup in Cloudflare R2 or any S3-compatible store, encrypted on the server with a
recovery key shown once (docs/BACKUP.md). `set` asks for the account id or endpoint, bucket, access
key id and secret (no echo; or key=value lines on stdin) and checks them by writing, reading and
listing a test object before it saves anything. `test` repeats that check; its `overwrite` and
`delete` rows say whether this key could replace or erase a backup (`delete refused` is the safe
setup; pruning is then left to a lifecycle rule of the bucket). With offsite on, `ls` has a WHERE
column (`local`, `local + offsite`, `offsite only`, `local, uploading`, `local, upload failed`), and
`restore` and `pull` fetch an offsite-only backup first (verified).
Example: `tando backup pull 20261113-171815-manual backup.tar`

### restore
`tando restore <backup id> [-a app] [--yes]` · `tando restore --from-host <host id> [app...|--all] [--yes]`.
Flags: `-a -H --yes --from-host --all`.
The first form is `tando backup restore`. `--from-host` recreates the apps of another server (one
that is lost) on this one from the offsite bucket: runtimes, env (set on the server, never through
the laptop), settings, domains, then the newest backup's data and database. Releases are not in
backups: it prints the `tando up` to run in each project. Runbook: docs/BACKUP.md.
Example: `tando restore --from-host 3f9a01c2b7de --all -H newvps`

### ls
`tando ls [-H host] [--all] [--all-rows] [--watch N | --follow] [--json] [--check]`. Arguments: none. `-a` is refused.

what needs attention (a server not answering, an app down, an alert firing, host care to do,

### snapshot
`tando snapshot --json [-H host | --all] [--app A] [--range 1h|24h|7d]`,
`tando snapshot --json --follow [-H host]`. Flags: `-a -H --all
--app --range --json --follow`. Arguments: none.

Everything a dashboard shows of a server in ONE ssh exec per host (as `tando top` reads its

parallel, each with a timeout (`TANDO_SNAPSHOT_TIMEOUT`, 15 s); a server that did not answer is

null once the audit log has rotated past it), `metrics` (`range`, `bucket_s`, `points`, `from`,

interpolated; 1h = 60 x 60 s, 24h = 144 x 600 s (the default), 7d = 168 x 3600 s; metrics keep 3.5
to 7 days), `health` (as `health --json` for the app, plus `last_ms`, `series` (the average probe
time of each of the last 24 hours, `t` from the server's clock) and `incidents`; null without
alerts) and `database` (when the app has one: `bytes`, `connections`, `connection_limit`; with the
database's samples (docs/MONITORING.md, PostgreSQL) also `series`, the same buckets as `metrics`:
`t`, `max_connections`, the sessions `active`, `idle`, `idle_in_transaction`, `waiting` (the
bucket's highest), `commits_per_s`, `rollbacks_per_s`, `rows_returned_per_s`, `rows_fetched_per_s`,
`rows_inserted_per_s`, `rows_updated_per_s`, `rows_deleted_per_s`, `cache_hit_pct`, `deadlocks`,

`checkpoints_requested`, `wal_bytes_per_s` (the server's); null where there was no sample or, for

`server_version_num`, `max_connections`, the sessions, the two ages, `xid_age`, `wraparound_pct`,
`size_bytes`, `stats_reset`) and `top_queries` (null unless `host setup --pg-stat-statements`:

at most 500 characters)). `--range` without `--app` (one host) adds
`host_metrics` instead: the same `range` .. `data_since` and a `series` of `t`, `load` (the

### health

### host
`tando host add <name> <user@address> [--port N] [--key FILE] [--yes] [--force] [--no-check]`
`tando host setup <name> [apps_domain=D] [tls=auto|internal|off] [setting=value ...] [--pg-stat-statements] [--pg-restart] [--yes]`
`tando host ls` · `tando host rm <name>` · `tando host rename <old> <new>` · `tando host rename --drop-alias <old>`
Flags: `--port --key --insecure-test --no-check --deploy --force --yes --drop-alias --pg-stat-statements --pg-restart`. Subcommands: add (2),
ls (default, 0), setup (1+), rm (1), rename (1-2).
`ls` shows each server's `user@address` (TARGET) as registered; a name is shown as is, never
looked up. `rename` changes a server's name on this laptop only (no server stores it; its audit
log and deploy records keep `user@machine` and the ssh address, so history is unchanged). It is
refused when the new name exists, when it breaks the host-name rule, or while a command that
changes the server runs for the old name (each such command marks `~/.config/tando/run/<host>.<pid>`
while it runs). It moves `hosts/<old>`, `cache/apps.<old>`, `last-host`, `tando go`'s answers,
`host =` in `tando.conf` and `.tando/target` of the current directory, closes the old ssh
connection and drops the dashboard's `cache/ls-all.json`. The old name stays an alias
(`~/.config/tando/renamed/<old>`, `alias=<new>`): a `tando.conf` or `-H <old>` elsewhere keeps
working with the note `host <old> was renamed to <new>`; `--drop-alias <old>` removes it.
`add` checks the login and shows the host key to trust (`--yes` trusts without asking,
`--no-check` saves without connecting, `--force` replaces an entry). `setup` installs rsync, curl,
nftables, Caddy, the firewall unit, timers and journals; safe to re-run. Settings: `apps_domain=`,
`tls=`, `public_port=`, `node=`, `python=yes`, `podman=yes`, `postgres=yes`, `postgres_version=N`
(only after moving the databases by hand: "Upgrading PostgreSQL"), `swap=yes|no`,
`ufw=no`, `domain_tls=internal`; also `app_max_mb=`, `ci_max_mb=`, `ci_max_files=`,
`ci_max_file_mb=`, `unit_drop=`, `journal_max=` (not in help.txt), and the per-client limits on ports
80/443: `rate_limit=on|off|auto` (auto: on when tando owns Caddy), `conn_limit=N` (connections at
once per client address, IPv6 /64; default 200), `conn_rate=N` (new connections per second, burst
3x; default 100), and per app's user `conn_out=N` (connections at once, default 2048), `dns_rate=N`
(DNS packets a second, default 200) ("Limits and load"). Scale (docs/ARCHITECTURE.md, "Many apps on one server"): `port_min=`,
`port_max=` (app ports, default 4100-4999), `preflight_min=`, `preflight_max=` (pre-flight ports,
default 14100-14999; the ranges must not overlap or hold 2019 or 5432), `uid_min=`, `uid_max=`
(new app users' ids, default 30000-39999), `mem_overcommit=` (default 1.5; 0 turns the check off),
`job_slots=`, `backup_window=HH:MM-HH:MM` (default 01:00-05:00, the server's time),
`backup_jobs=1` to `4` (backups at once, default 1), `log_budget=` (all apps' logs together, default
`auto`: 20% of the log file system). Without `apps_domain`, links use
`<ip-with-dashes>.sslip.io` (an outside service). `--deploy` and `--insecure-test` are not in the
usage (docs/DEV-NOTES.md, mismatch 7). `care=on|off`: host care's security updates (on by default where tando
installed Caddy itself; docs/HOSTCARE.md). `--pg-stat-statements` (with PostgreSQL on the server):
turns on `pg_stat_statements` for the top statements of each app's database (`tando snapshot`'s
`database.top_queries`). It adds the module to `shared_preload_libraries`, so PostgreSQL restarts
once (every app's database is away for a few seconds); setup asks first, `--yes` does not ask.
A later run restarts nothing. The extension goes in the `postgres` database only, with
`track_utility` off (docs/MONITORING.md, PostgreSQL). Never turned on by anything else.
With PostgreSQL on the server, setup also sizes it from the server's RAM and runs pgbouncer
("Database connections and pgbouncer" below). `--pg-restart`: when the sized
`max_connections` or `shared_buffers` differ from what PostgreSQL runs with (a server set up by an
older tando, more RAM, `pg_max_connections=N`), they need a restart, which drops every app's
database connections for a few seconds; setup then leaves PostgreSQL running, says so in its
database step and in `tando doctor` (row `postgresql settings`), and restarts it only with
`--pg-restart` (asked first, `--yes` does not ask). A server with no app database yet restarts by
itself. `pg_max_connections=N` (20 to 9999; `auto`: from RAM again) sets max_connections.
Example: `tando host setup vps apps_domain=apps.example.com tls=auto`

### adopt
`tando adopt plan|apply <unit> [--health /path] [--no-jobs] [--yes] [--accept-502]` ·
`tando adopt undo|status <app>` · `tando adopt site <app|unit> [--health /path] [--apply]`. Flags:
`-H --health --no-jobs --yes --apply --accept-502`. Subcommands: plan, apply, undo, status, site
(1 argument each). `-a` is refused.
Takes over a hand-deployed Next.js app (systemd unit behind Caddy) in place: `plan` is read-only,
`apply` backs up, switches and rolls back on failure, `undo` returns to the recorded state.
The order is `plan`, `site --apply`, `apply`.
`site` shows what your own Caddy site lacks next to one tando renders: `lb_try_duration` in the
app's `reverse_proxy` (requests wait while the app restarts instead of getting 502) and the request
log that `tando requests`, `tando errors` and the 5xx alert read. `site --apply` adds them: a copy of
the Caddyfile is kept, the new file is validated, its ports are checked (one another program holds
is refused before anything is reloaded), Caddy is reloaded and the app is checked through it; a
failure puts the previous file back. Caddy is restarted only after a reload that failed, and only
when the previous file loads: a failed reload leaves part of the rejected configuration serving
until a restart ("What the hold covers, exactly" under Limits and load). When the previous file
does not load either, Caddy is left running and the output says to fix the file and restart it. A site it cannot read with certainty
(several `reverse_proxy` lines to the port, a log of its own, an imported file) is not edited: the
lines to add by hand are printed.
Before adoption `site` takes the unit, as `plan` does (with the same `--health`), and reports and
adds the hold only: the request log needs the app's log directory, so it comes with a second
`site --apply` after adoption. The copy of the Caddyfile is kept in `/opt/tando/adopt/<unit>/`
(root only) before adoption and in `/var/backups/tando/<app>/` after it.
Without the hold, every request that arrives while the app restarts gets 502: during the adoption
and during every later deploy, rollback or restart. `plan` says so in a section of its own, with
the command that adds the hold, and `apply` refuses to start (nothing is changed) unless
`--accept-502` is given. That flag is also the way to adopt behind a site `site` cannot edit, when
you do not add the two lines by hand first. `apply` itself never edits the Caddyfile, so `undo`
returns to the site as it was when `apply` started: with the hold, if you added it before.
See docs/MIGRATION.md.
Example: `tando adopt plan bakery -H vps --health /order/new`

## The release command

`release = <command>` in tando.conf: a command tando runs on the server once per deploy, before
the new release takes traffic. It is meant for database migrations.

```
release = node scripts/migrate.js
release_timeout = 120              # seconds, 1 to 3600; default 300
# release_shell = true             # run it with sh -c (&&, |, $VARS, quotes)
```

- **When.** After the new release passed its pre-flight (started on a spare port, healthy) and
  after the pre-deploy backup of the data directory and the database was taken, before the
  switch. In the deploy box and in `tando history` it is its own phase (`release`, `RELCMD`).
- **The pre-flight runs before it.** The new release is started and health-checked against the
  data as the old release left it, so its health check must pass before the migration too.
- **How.** In the new release's directory, as the app's user, with the app's environment
  (`tando env`, `DATABASE_URL`, `TANDO_DATA_DIR`), sandbox and limits: what a scheduled job gets.
  It cannot listen on a port. `PORT` is the app's port, `TANDO_RELEASE` the new release's id. A
  Python app's virtualenv is on `PATH`. Without `release_shell = true` the command is split on
  spaces and run with no shell, like `start`; shell syntax in it (quotes, `&&`, `|`, `$VAR`) is
  refused, because it would reach the program as literal words.
- **When it fails** (a non-zero exit, or longer than `release_timeout`): the deploy fails with a
  non-zero exit status, nothing is switched, the old release keeps serving. The deploy box and
  `tando history` say so with the command's last lines of output; all of its output:
  `tando logs --deploy <release id>` (source `release`).
- **tando never restores the database or the data by itself.** The old release is live and writes
  to the same database while the command runs; putting a backup back would discard those writes.
  What a failed command changed stays changed. The failure message names the pre-deploy backup
  taken just before it: `tando backup restore <id>` puts it back when you decide to (what the backup holds comes back;
  a table the command created after it is not dropped).
- **`tando rollback` does not undo a migration.** It switches the code back; the database stays as
  the command left it. Write migrations the previous release can still run with (add a column
  first, remove it a deploy later).
- **It must be safe to run twice.** It runs on every deploy, of unchanged code too (with a release
  command a deploy is never "already live"), and again when a deploy is repeated after a failure.
  It does not run on `tando rollback`, `restart`, `env set` or an automatic rollback.
- **If the server restarts or the activation is killed while it runs**, the command is stopped
  where it was, the deploy is recorded as failed ("interrupted during release") and the old
  release keeps serving. A migration that was cut off is in whatever state its own transactions
  left it.
- **Recipes.** node, next and python. Refused for `static` (no process, nothing to run it as) and
  for `container` (the release is an image: run the migration in its entrypoint).
- With a deploy key (CI) the command is the one of the admin's last `tando up` or `tando deploy`,
  like every other setting.

## Limits and load

What keeps one app, or one client, from taking the server down. Per app in tando.conf, applied at
the next deploy; per host with `tando host setup <host> key=value`.

| Setting | Default | Limits | When it trips, a visitor or the app sees |
|---|---|---|---|
| `memory =` | 256M | each unit of the app; all its units together 3x | the process is killed (OOM) and restarted; node/next also get `NODE_OPTIONS=--max-old-space-size` at 70% so V8 exits instead of thrashing |
| `cpu =` | none | the app's units together (`50%` of a core, or `1.5` cores) | the app runs slower; neighbours keep their share |
| `tasks =` | 1024 | processes and threads of all its units | fork/thread creation fails in the app |
| `max_conns =` | 256 | Caddy's connections to the app | requests wait in Caddy for a free connection |
| `max_requests =` | none (off) | requests in flight through Caddy | over it a request waits up to the hold and then gets `503` "<app> is busy ..." with `Retry-After: 5` |
| `hold =` | 15, or `health_timeout` | seconds Caddy holds a request while the app (re)starts | after it the visitor gets 502; with `max_requests` also how long a request over the limit waits for its 503 |
| `stop_timeout =` | 10 | seconds a stopping process may finish its requests | it is killed (requests it still had fail); Caddy holds new ones meanwhile |
| host `conn_limit=` | 200 | connections at once per client address (IPv6: per /64) on ports 80/443 | further connections are reset |
| host `conn_rate=` | 100 | new connections a second per client address, burst 3x | further SYNs are dropped: the client retries a second later |
| host `rate_limit=` | auto | on, off, or auto: on only where tando owns Caddy (it installed it, or the Caddyfile has no other site) | `tando doctor` row "client limits" shows how often they tripped |
| `priority =` | normal | CPU weight of the app's slice under contention: high 200, normal 100, low 50 (and the OOM order, MemoryLow for high) | a busy `low` app yields CPU to the others first |
| `tmp_size =` | 64M | the app's `/tmp` and `/var/tmp`: each a tmpfs of its own, counted in its memory (not a directory on the disk every app shares; a venv or container build keeps a private /tmp on disk) | writes fail with "No space left on device" |
| `io =` | none | MB/s of reads and of writes on the disk of the app's directory (`IORead/WriteBandwidthMax`; only where the cgroup io controller is) | the app's disk I/O is slowed |
| `disk =` | host `app_max_mb` | the app's disk share for alerts (`2G`, `500M`): its files and database | alert `disk_warn` (low) from 80%, `disk` over it; no hard quota |
| host `conn_out=` | 2048 | TCP and UDP connections one app's user holds at once (the kernel's connection table is the host's) | further connects are refused at once (`ECONNREFUSED`) |
| host `dns_rate=` | 200 | DNS packets a second one app's user sends (burst 2x), the resolver all apps share | further lookups fail at once |
| (`db_pool` x 20) | 100 | connections one app's user holds to pgbouncer and PostgreSQL together (pgbouncer's 5000 client slots are every app's) | further connects are refused |

The core is protected the other way round: `host setup` gives Caddy (64 MB), sshd (32 MB),
tandod (32 MB), pgbouncer (32 MB) and PostgreSQL (its shared buffers + 32 MB) a `MemoryLow=`
(reclaim takes from apps first) and `system.slice` their sum. On ext2/3/4, the blocks the file
system of /opt/tando reserves (often 5%) go to group `tando-core` too (PostgreSQL and Caddy are
in it; root always has them): an app that fills the disk leaves the database and Caddy room. The
running PostgreSQL and Caddy get the group at their next restart. The `tando doctor` row "app
limits" counts what the per-app rules refused.

### Scale to zero: idle_stop

`idle_stop = 6h` (also `10m`, `30s`; `on` is 6h; default off) stops the app's web process after
that long without a request and starts it again on the next one, so an app nobody uses holds
no memory. Only the web process: the app's workers and scheduled jobs run as before. For node,
next and python apps; not for static sites (they have no process) nor containers. How: Caddy proxies to the app's wake socket `/run/tando-wake/<app>.sock` (systemd's,
group caddy) instead of its port. A connection there starts `tando-<app>_wake.service`
(`systemd-socket-proxyd` as the app's user, `--exit-idle-time=<idle_stop>`), which needs
`tando-<app>.service`; that unit is ready once its port answers and stops when the proxy exits
(`StopWhenUnneeded`). The first request waits in the socket's queue while the app starts: about
0.1-0.3 s for a small Node or Go app (docs/ARCHITECTURE.md has none of this yet; the numbers are
in the squeeze audit). `tando ls` shows such an app as `idle`; the monitor asks its health on its
port only while it runs (a probe through Caddy would keep it awake) and raises no down alert while
it is idle; the per-minute recovery leaves it idle. A deploy of an idle app starts the new release
(it goes idle again later). Caddy keeps no pooled connection to it (`keepalive off`), so the
timer starts with the last request. A restart stops requests in flight.
### Database connections and pgbouncer

Apps with `database = postgres` share one PostgreSQL. `tando host setup` sizes it from the
server's RAM (MemTotal, or a container's memory limit when lower):

| Setting | Value | On 8 GB |
|---|---|---|
| `max_connections` | one per 80 MB, in tens, 50 to 400 (`pg_max_connections=N` in host setup) | 100 |
| `shared_buffers` | 15% of RAM | about 1.2 GB |
| `work_mem` | RAM / max_connections / 16, 2 to 32 MB | 4 MB |
| `maintenance_work_mem`, `effective_cache_size` | 1/32 of RAM (16 MB to 1 GB), half of RAM | 245 MB, 3.9 GB |

They are in `/etc/postgresql/<version>/main/conf.d/tando.conf`. A change of `max_connections` or
`shared_buffers` waits for `tando host setup <host> --pg-restart` (see host setup above).

**pgbouncer.** Setup also runs one pgbouncer for all apps, on 127.0.0.1:6432 only (no unix
socket; apps without a database cannot reach it, as with 5432), in transaction pooling: a server
connection belongs to an app only for the length of one transaction, and is closed after a minute
idle. Each app gets at most `db_pool` server connections (default 5) however many its own pool
opens, so 100 apps fit in about 100 PostgreSQL connections. pgbouncer checks the app's password
against the role's SCRAM secret (`/etc/pgbouncer/userlist.txt`, root:postgres 0640, kept in step
when an app is created, destroyed or gets a new password); `/etc/pgbouncer/pgbouncer.ini` is
rewritten by tando, edits there do not last.

| Variable | Points at | Used by |
|---|---|---|
| `DATABASE_URL` | pgbouncer (6432), or PostgreSQL (5432) with `db_direct = true` | the app, its workers and jobs |
| `DATABASE_URL_DIRECT` | PostgreSQL (5432), always | the release command, which gets it as `DATABASE_URL` |

tando's backups and restores, `tando db psql`, the studio and tando-watch connect to PostgreSQL
directly. **What transaction pooling does not keep** between two transactions of the app:
`LISTEN`/`NOTIFY`, session advisory locks (`pg_advisory_lock`; `pg_advisory_xact_lock` works),
session `SET` (use `SET LOCAL` inside the transaction), temporary tables kept across transactions,
`WITH HOLD` cursors, and prepared statements with drivers that prepare them by SQL (`PREPARE`).
Protocol-level prepared statements work with pgbouncer 1.21 and newer (Ubuntu 24.04 has 1.22);
an older pgbouncer needs them off in the driver (for example `prepareThreshold=0` in JDBC, or
`statement_cache_size=0` in asyncpg). An app that needs any of these sets `db_direct = true`.

**Per app in tando.conf:** `db_pool = N` (1 to 999, default 5): pgbouncer's server connections for
the app; with `db_direct = true`, what the app's own pool should stay within. The role may hold
`db_pool + 5` connections (the 5 for migrations, backups, the studio and `db psql`). A deploy is
refused when the apps' `db_pool` together would pass max_connections less 8 (3 for the superuser,
5 for tando), unless it does not raise the app's own. `db_direct = true` gives the app PostgreSQL
itself (and its own pool is then capped by the role's limit only).

**Upgrading.** `tando host setup` installs pgbouncer but leaves running apps alone: an app moves
to pgbouncer on its next deploy, unless it sets `db_direct = true`. Setup says how many apps are
still direct. A deploy whose role pgbouncer does not let in (pgbouncer down, for example) keeps
the direct URL and warns. A rollback keeps the current `DATABASE_URL`; to go back to a direct
connection set `db_direct = true` and deploy. An older tando agent on the server keeps working
with a pooled `DATABASE_URL`. `tando db` shows how the app connects.

### Database limits

Each app's role gets limits, so one query or one forgotten transaction cannot take the database
from the others. Per app in tando.conf; `off` turns one off.

| Setting | Default | Limits | When it trips, the app sees |
|---|---|---|---|
| `db_statement_timeout =` | 30s | how long one statement may run (waiting for a lock counts) | `canceling statement due to statement timeout`; the connection stays usable |
| `db_idle_tx_timeout =` | 5m | how long a connection may sit idle inside an open transaction (it holds locks and blocks cleanup) | the connection is closed; the transaction is rolled back |
| `db_temp_limit =` | 1G | temporary files of one connection (large sorts, hashes, index builds) | `temporary file size exceeds "temp_file_limit"`; the statement fails |

Times are `500ms`, `30s`, `5m`, `2h`; sizes `512M`, `2G`. They are set on the role (`ALTER ROLE ...
SET`) by a deploy when it goes live (before its release command, if it has one; a deploy that does not go live leaves the live ones) and by `tando host setup`, which also gives them to
apps deployed by an older tando. A running app gets them with its next connection (a deploy
restarts it). `tando db` shows what is set. `lock_timeout` is not set.

**What they do not stop.** The two timeouts are ordinary PostgreSQL settings that any session may
change, and PostgreSQL has no way to forbid that: they catch mistakes, not an app that sets them
to 0 on every connection. `db_temp_limit` is different: only a superuser can change it, so the app
cannot raise it; change it in tando.conf.

**A long migration** raises the timeout for itself, in the session or in its transaction:

```sql
SET statement_timeout = 0;                 -- this session
BEGIN; SET LOCAL statement_timeout = '10min'; CREATE INDEX ...; COMMIT;   -- this transaction only
```

An index on a large table sorts through temporary files: when a migration fails with
`temp_file_limit`, raise `db_temp_limit` in tando.conf and deploy.

**Not under the timeouts:** tando's backups and restores (`pg_dump` and `pg_restore` set both to 0
themselves; a restore also lifts the temp file limit while it runs, with the app stopped, and sets
it again after), and `tando db psql`, where a person runs a long query or pauses inside a
transaction on purpose (the temp file limit applies there too).

**Out of memory.** The kernel's OOM killer takes an app first (score 500), then a single
PostgreSQL connection's process (0), and the postmaster last (-900): killing the postmaster would
take every app's database down. The Ubuntu packages set this; tando pins it in
`/etc/systemd/system/postgresql@.service.d/tando.conf` and `tando doctor` reads the live values
(row `postgresql memory`). `vm.overcommit_memory` is not changed: strict overcommit, which the
PostgreSQL manual suggests for a dedicated database server, makes Node and Python apps on the same
small server fail to start.

### Upgrading PostgreSQL

tando records the major version whose cluster holds the apps' databases (`postgres_version` in
`/opt/tando/host.conf`) the first time it uses PostgreSQL, and keeps using that one. A distribution
upgrade can install a newer major beside it, with an empty cluster on another port: tando does not
switch to it, and `tando doctor` says so (row `postgresql version`). Nothing needs doing until the
old version stops getting updates.

Moving the databases is manual. **This runbook has not been rehearsed** (the test server's
distribution has one major version only): try it on a copy of the server first.

1. A backup of every app with a database, and a copy off the server:
   `tando backup now -a <app>`, `tando backup pull <id> <file> -a <app>`. Note each id.
2. Stop those apps: `tando stop -a <app>`.
3. On the server, put the new cluster on port 5432 and the old one aside (here from 18 to 19):
   `pg_lsclusters`, then `sudo pg_conftool 18 main set port 5433`,
   `sudo pg_conftool 19 main set port 5432`, `sudo systemctl restart postgresql`.
4. `tando host setup <host> postgres_version=19`. tando refuses unless 19/main listens on 5432. It
   writes its settings for the new cluster, records the version, and creates each app's role and
   empty database there (with a new password in the app's `DATABASE_URL`).
5. For each app: `tando backup restore <id> --yes -a <app>` puts the data back and starts the app.
6. `tando doctor`, and look at each app. When all is well, remove the old cluster:
   `sudo pg_dropcluster --stop 18 main`. Until then, going back is steps 3 and 4 with the versions
   swapped (the old cluster still has its data and the old passwords; restore after that as well,
   since step 4 sets new passwords).

**What the hold covers, exactly.** While an app restarts (deploy, rollback, `restart`, adoption,
`adopt undo`), Caddy holds a request up to the hold and sends it once the app listens, so it is
answered late instead of failing. Held: every request that cannot connect, whatever its method
(nothing reached the app), and a GET whose connection to the app broke (Caddy 2.6 to 2.10 retry a
GET on any error; nothing else needs adding for that). Not held, and answered 502:
- a request that is not a GET (POST, PUT, DELETE, HEAD) already sent on a kept-alive connection
  that the stopping app then closed. It may have been processed, so neither Caddy nor tando sends it
  again. The window is the instant the app closes an idle connection Caddy has just picked; the
  tests (test/e2e-adopt.sh A7f) have not met it;
- a request the old process still had when it was killed after `stop_timeout`;
- a restart longer than the hold;
- a request held while Caddy reloads: the reload ends it. tando's own site changes wait until the
  app listens again; a reload you run yourself at that moment is not covered;
- every request, held or not, that reaches what is left of a reload that failed while Caddy started
  its servers: Caddy (2.6 to 2.10) keeps the servers it had started, with the rejected
  configuration and nothing held, until it restarts. tando refuses a Caddyfile that listens on a
  port another program holds (the usual cause) before reloading; after a failed reload it puts the
  previous file back and restarts Caddy when that file loads; `tando doctor` shows a failed reload
  since Caddy started (row `caddy reload`) and says to restart Caddy.

Loopback is never limited (tando's probes, an app calling itself through Caddy); ssh is not touched.
All apps together get half the CPU weight of the system services (Caddy, sshd, the agent), and an
app is the first thing the kernel kills when memory runs out. tando-watch restarts an app whose
unit runs but that does not answer (`liveness`, docs/MONITORING.md), never one that is only busy:
it asks the app's port directly first.
**Shedding is off by default.** Caddy 2.6 has one retry loop for "the app is full" and "the app is
restarting", so a request over `max_requests` gets its 503 only after the hold. With the 15 s hold
and clients that give up after 10 s, shedding turned a burst into timeouts (load test: 10,000
keep-alive connections to hello gave 3,400 rps with 1,700 timeouts with it, 5,560 rps and none
without). Set `max_requests` together with a short `hold` (2-3 s) for an app that starts in about a
second; a slow-starting app needs the long hold, and then shedding does not help.
**Per-request rate limits per app** (requests per second per client) need a Caddy plugin
(rate_limit) that the distribution's Caddy does not have: not offered. `max_requests` and the
per-client connection limits cover a flood; put a CDN or the plugin in front for more.
**Sizing:** max_conns about the number of requests the app can work on at once (a Node app: its
event loop answers many; a Python app with N workers: N to 2N); max_requests is the queue on top;
memory the app's peak, measured with `tando top` under load.
**Disk:** a deploy needs about 3x the release's size free (the upload in incoming/, the new
release, the kept ones), and as many free inodes as it has files; an upload over `app_max_mb`
(host setup) is refused before it is sent. **Caddy reloads:** `stop`, `start`, a domain change or
a new app reload Caddy's whole config; Caddy 2.6 finishes requests in flight but closes idle
keep-alive connections of every site it serves (clients reconnect; one that sends on a connection
being closed sees a reset). A deploy itself does not reload Caddy when the site did not change.
**Restarts under load:** an app that on SIGTERM only calls `server.close()` waits for every
keep-alive connection, and Caddy keeps its connections busy under load: the old process lives until
stop_timeout. Close idle connections too and answer with `Connection: close` from then on (see
examples/hello/server.js); Express and Fastify servers have the same `closeIdleConnections()`.

`tando addon install dashboard [--version V] [--from PATH|URL] [--sha256 HEX] [--insecure]` ·
`tando addon uninstall dashboard` · `tando addon status`. The dashboard (`addons/dashboard`) is not in
the main archive: it ships as its own release asset, `tando-dash-<v>-<darwin-universal|linux-amd64|
linux-arm64>.tar.gz` with a `.sha256`, built by `scripts/release-dashboard.sh`.
- `install` downloads the asset of this client's version (or `--version V`) for this OS and CPU from
  the GitHub release of the same repository as `install.sh`, or takes `--from` (a path, `file://` or
  `https://`; plain `http://` only with `--insecure`). It refuses to go on when the checksum does not
  match, or when there is none: the `.sha256` next to the archive, or `--sha256 HEX` (which wins).
  Nothing is unpacked before the checksum is right; names outside the archive's directory and links
  are refused; the new `tando-dash` must run (`--version`) before anything is put in place.
  It installs `~/.local/lib/tando-dash/<v>/` with a `current` link, links `~/.local/bin/tando-dash`
  (a file of your own there is not overwritten), and on macOS removes the quarantine attribute from
  the files of the verified archive and from nothing else. Older version directories are removed.
- `uninstall` stops a running `tando-dash`, removes the binary, its links, `dash.lock` and the
  dashboard's cache files (`ls-all.json`, sessions, idempotency records, last port). Settings, hosts
  and everything else in `~/.config/tando` stay.
- `status`: the installed version against this client's, and whether `tando-dash` runs (pid, port).
Example: `tando addon install dashboard`

### dashboard
`tando dashboard [--no-open] [--idle 30m] [--port N]`: runs `tando-dash` (the add-on) with these
arguments and this tando. It prints a one-time link and opens it in the browser; when one is already
running it asks that one for a fresh link instead of starting another. Without the add-on it says
`tando addon install dashboard`. The flags are `tando-dash`'s (`tando-dash --help`).
Example: `tando dashboard`

### menubar
`tando menubar install [--dry-run]` · `uninstall [--dry-run]` · `status` · `build --out DIR`. macOS
only. A menu bar icon for every registered server, and an outside heartbeat from the laptop.
- `install` compiles `macos/menubar/*.swift` with `swiftc` (the Command Line Tools are enough:
  `xcode-select --install`; no Xcode, no packages), makes `~/Applications/tando.app` (no Dock icon),
  signs it ad hoc (`codesign -s -`), writes `$TANDO_CONFIG_DIR/menubar.conf` (which `tando` to run:
  the launcher you ran install with, since a LaunchAgent has no PATH of yours) and the LaunchAgent
  `~/Library/LaunchAgents/local.tando.menubar.plist` (RunAtLoad: it starts at login; Quit stops it
  until the next login), and starts it. `--dry-run` prints all of that and changes nothing. Run it
  again after a tando update: it rebuilds the app and keeps your settings.
- `uninstall` stops it and removes the app, the LaunchAgent and menubar.conf. `status`: installed,
  running, which tando, the interval. `build --out DIR` only compiles and signs `DIR/tando.app`.
- **What it checks**, every `interval` seconds (menubar.conf, default 60), one check at a time, each
  stopped after `timeout` seconds (default 45): `tando ls --all --json` (one ssh connection per
  server: the apps, their state and the firing alerts), then a GET of every running app's link from
  the laptop (8 s limit; any answer below 500 counts as up). Also at once after the Mac wakes or
  comes back online.
- **The icon.** Plain: all is well. A red count: the problems now, where each is one of a server the
  laptop could not reach two checks in a row (the menu shows the error from the first), an app with something wrong (down or failed, a link that failed two checks in
  a row, or a firing alert: an app counts once), and a firing host check (disk, memory, ...). Dimmed:
  nothing could be checked (the laptop is offline, or tando failed or timed out); the last menu stays.
  Pending alerts and apps you stopped are not problems.
- **The menu.** The last check time; per server its apps with a coloured dot and their state (each
  with "Open <link>" and "Open status in Terminal", which runs `tando status <app> -H <server>`); a
  server it cannot reach, with the reason; the firing alerts; Open dashboard (⌘D, below); Refresh now
  (⌘R); Open status in Terminal (`tando ls --all`); Quit.
- **Open dashboard** (⌘D) opens the dashboard add-on in a window of its own (a WKWebView; one window,
  reused; native title bar; at least 900x600, its size and place are remembered; ⌘R reloads, ⌘W closes
  the window and not the app; links to other sites open in your default browser, and the window never
  shows anything but `127.0.0.1:<port>`). It finds `tando-dash` (`~/.local/lib/tando-dash/current`,
  `~/.local/bin`, `PATH`), starts it (`--no-open`) when `~/.config/tando/dash.lock` names no running
  process (a lock left by a crash is told by its dead pid), and asks it for a fresh one-time link
  (`POST /api/newcode` with the lock's key). Without the add-on the row reads "Install dashboard…" and
  shows the one command, `tando addon install dashboard`. Closing the window ends the page; the idle
  `tando-dash` stops by itself. `tando-menubar --dash-url` does all of this but the window and prints the link.
- **The cache.** While `tando-dash` runs it writes `~/.config/tando/cache/ls-all.json` (the shape of
  `tando ls --all --json`). A check that finds it younger than `interval` reads it instead of running
  `tando ls --all --json` (no second set of ssh connections); an older or unreadable file is ignored.
  `--once` prints `source: cache` or `source: tando`.
- **Notifications.** Once per new problem (more than 3 at once: one summary) and once when it is
  resolved. A server that cannot be reached hides its other problems until it answers again (they
  are not reported as resolved). Delivered through macOS notifications (allow them when asked;
  System Settings, Notifications, tando); if the system refuses to register the ad-hoc signed app,
  through `osascript` (shown as Script Editor). `notify=off` in menubar.conf turns them off.
- **Only while the laptop is on and online.** This heartbeat watches from outside the server, so it
  sees what a visitor sees, but it is asleep when the laptop is. It complements `tando alerts
  heartbeat` to an outside service (docs/MONITORING.md, "From outside"), which keeps watching
  around the clock; it does not replace it.
- It stores no credentials (it runs your tando, which uses your ssh setup), opens no listening
  socket, and sends nothing anywhere but the ssh connections and the requests to your apps' links.
  The app's `--once [--checks N]` prints one check as text:
  `~/Applications/tando.app/Contents/MacOS/tando-menubar --once`.
Example: `tando menubar install`
